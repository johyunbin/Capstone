## A. 비용 모델(Cost Model) 한계 검증 및 보정

### 논문의 빈자리
Exqutor 논문 Section 6.8 한계점 #2에서 스스로 인정한 문제: "기존 데이터베이스의 비용 모델이 ANN 인덱스의 성능 특성을 제대로 반영하지 못해, **정확한 카디널리티가 있어도** 최적 계획을 선택하지 못할 수 있다." 즉, Exqutor가 카디널리티를 완벽히 맞춰줘도 옵티마이저가 여전히 틀릴 수 있다는 것인데, 이게 **실제로 얼마나 자주 발생하는지** 논문에서 정량적으로 다루지 않았다.

### 실험 아이디어
- pgvector에서 VAQ 쿼리를 실행하되, `pg_hint_plan`으로 **가능한 모든 실행 계획 조합**을 강제 지정
- 각 조합의 실제 실행 시간을 측정 → 진짜 최적 계획(oracle plan) 확인
- Exqutor가 정확한 카디널리티를 줬을 때 옵티마이저가 선택한 계획 vs oracle plan 비교
- **차이가 나는 패턴 분류**: 어떤 조인 방식에서? 어떤 스캔에서? 왜?

### 산출물
- "Exqutor + 비용 모델 보정" vs "Exqutor만" vs "기본 pgvector" 3단 비교표
- 비용 모델이 틀리는 패턴 카탈로그
- 보정 규칙(hint) 제안

### 난이도/현실성
- **난이도**: 중 (pg_hint_plan 사용법 학습 필요, 코드 수정은 불필요)
- **환경**: pgvector + pg_hint_plan만 있으면 됨
- **강점**: 논문 저자(교수님)가 인정한 한계를 직접 정량화 → 가장 직접적인 후속 연구

## B. 선택도(Selectivity) Sweep — 효과 경계 매핑

### 논문의 빈자리
Exqutor 논문은 몇 개 데이터셋과 고정된 거리 임계값 D에서 실험했다. **선택도를 연속적으로 변화시키면서** Exqutor 효과가 어떻게 달라지는지, 특히 "pgvector의 33.3% 고정 추정이 우연히 맞는 교차점(crossover point)"이 존재하는지는 다루지 않았다.

### 실험 아이디어
- 거리 임계값 D를 조절해서 선택도를 0.01% → 0.1% → 1% → 5% → 10% → 30% → 50% → 90%로 변화
- 각 선택도에서:
  - pgvector 기본 추정 카디널리티 vs 실제 카디널리티 (Q-error 측정)
  - 선택되는 실행 계획 변화 관찰 (Hash Join ↔ Nested Loop, Seq Scan ↔ Index Scan)
  - 실행 시간 변화 곡선
- **교차점 발견**: 선택도 33.3% 근처에서는 pgvector의 고정 추정이 우연히 맞을 것 → Exqutor 효과 최소화 예상

### 산출물
- 선택도 vs 실행시간 곡선 (Exqutor 적용 전/후)
- 선택도 vs Q-error 히트맵
- "Exqutor가 효과적인 선택도 영역" 시각화
- 실행 계획 전환점(tipping point) 카탈로그

### 난이도/현실성
- **난이도**: 하~중 (SQL에서 D값만 바꾸면 됨, 자동화 스크립트 필요)
- **강점**: A번의 **필수 선행 작업**이기도 함, 자문위원이 요구한 "데이터셋 + 대조군 + 평가지표" 세 가지를 가장 직관적으로 충족
- **약점**: 단독으로는 novelty가 부족할 수 있음 (but baseline으로는 필수)

## C. 복합 필터 조합의 카디널리티 오차 증폭

### 논문의 빈자리
Exqutor 벤치마크는 벡터 필터 1개 + 태그 필터 1개 조합 정도만 테스트. 실무 RAG에서 흔한 **날짜 범위 + 카테고리 + 가격대 + 벡터 유사도** 같은 복합 조건에서의 동작은 미확인. 필터가 겹칠수록 카디널리티 추정 오차가 곱셈적으로 증폭될 가능성이 있다.

### 실험 아이디어
- 벡터 검색 조건에 관계형 필터를 단계적으로 추가:
  1. 벡터 필터만
  2. 벡터 + 날짜 범위
  3. 벡터 + 날짜 + 카테고리 label
  4. 벡터 + 날짜 + 카테고리 + 가격 범위
- 각 단계에서 카디널리티 추정 오차(Q-error)와 실행 시간 변화 측정
- **필터 간 상관관계**가 있을 때 vs 독립일 때 비교 (예: 벡터 유사도가 높은 것이 특정 카테고리에 집중되는 경우)

### 산출물
- 필터 수 vs Q-error 증가 곡선
- 상관/독립 필터 시나리오별 비교표
- 복합 필터 환경에서의 실행 계획 변화 패턴

### 난이도/현실성
- **난이도**: 중 (쿼리 설계가 핵심, 데이터 준비 필요)
- **강점**: 실무 관련성 높음, 재현이 아이디어와 직접 연결
- **약점**: 데이터 스키마를 잘 설계해야 의미 있는 결과가 나옴

## D. Top-k vs Range Query 비교 실험

### 논문의 빈자리
Exqutor는 **범위 검색(range query)만** 다룬다. 실무에서 압도적으로 많이 쓰이는 `ORDER BY distance LIMIT k` 형태의 **top-k 검색**은 범위와 카디널리티 추정 문제의 성격이 다르다. top-k는 결과 수가 k로 고정되므로 벡터 연산 자체의 카디널리티는 확정적이지만, **조인 이후의** 행 수 추정에서 여전히 문제가 생길 수 있다.

### 실험 아이디어
- 같은 의미의 쿼리를 range와 top-k 두 버전으로 작성
- pgvector가 top-k에서 카디널리티를 어떻게 추정하는지 EXPLAIN ANALYZE 분석
- top-k 쿼리에서도 조인 순서/방식이 비최적인 경우가 있는지 확인
- Exqutor의 ECQO가 top-k에도 적용 가능한지 이론적 검토

### 산출물
- Range vs Top-k 실행 계획 비교표
- Top-k에서의 카디널리티 추정 정확도 측정
- "Top-k에도 Exqutor가 필요한가?" 에 대한 답변

### 난이도/현실성
- **난이도**: 하 (쿼리 변환만 하면 됨)
- **강점**: 실무 적용성 관점에서 반드시 해야 할 질문
- **약점**: 결과가 "top-k에서는 문제 없음"이 나올 수도 있음 → 그래도 부정적 결과 자체가 가치 있음

## E. 필터 적용 순서(Filter Ordering) 최적화

### 논문의 빈자리 + 팀 아이디어
재현이가 제안한 방향과 직접 연결: "많이 retrieval되는 조건과 적게 retrieval되는 조건이 있을 때, 어떤 순서로 적용해야 최적인가?" Exqutor는 카디널리티를 정확히 알려주지만, **그 정보를 바탕으로 필터 적용 순서를 어떻게 결정해야 하는지**에 대한 전략은 제시하지 않았다.

### 실험 아이디어
- 선택도가 서로 다른 두 필터 조건을 가진 쿼리 설계:
  - 벡터 유사도 (선택도 높음: 많은 결과 반환) + 정확한 라벨 매칭 (선택도 낮음: 적은 결과)
  - 벡터 유사도 (선택도 낮음) + 넓은 날짜 범위 (선택도 높음)
- `pg_hint_plan`으로 필터 적용 순서를 강제:
  - 벡터 먼저 → 관계형 필터 후
  - 관계형 필터 먼저 → 벡터 후
  - 옵티마이저 자동 선택
- 각 전략의 실행 시간, I/O 비용, 메모리 사용량 비교
- **선택도 비율에 따른 최적 순서** 규칙 도출

### 산출물
- 필터 순서별 실행 시간 비교표
- "벡터 선택도 / 관계형 선택도 비율"에 따른 최적 전략 가이드라인
- 옵티마이저 자동 선택이 틀리는 사례 카탈로그

### 난이도/현실성
- **난이도**: 중
- **강점**: 팀 내 아이디어(재현)를 발전시킨 것이라 팀원 모두 이해하기 쉬움, 실용적 가이드라인 산출 가능
- **약점**: A, B번 실험이 선행되어야 의미 있는 결과

## F. 실제 RAG 임베딩 분포에서의 검증

### 논문의 빈자리
Exqutor는 DEEP, SIFT, SimSearchNet++, YFCC, WIKI 같은 연구용 벡터 데이터셋만 사용. 실제 RAG 파이프라인에서 `text-embedding-3-small`(OpenAI)이나 `all-MiniLM-L6-v2`(sentence-transformers) 등으로 생성한 임베딩은 분포 특성이 다를 수 있다. 특히 **코사인 유사도 기반 임베딩**은 유닛 구 위에 분포하므로 유클리드 거리 기반과 다른 패턴을 보일 수 있다.

### 실험 아이디어
- 실제 텍스트 데이터(예: 한국어 Wikipedia, 뉴스 기사)를 sentence-transformers로 임베딩
- 10만~100만건 규모로 pgvector에 로드
- 같은 Exqutor 쿼리 패턴을 적용해서 연구용 데이터셋과 비교
- **거리 분포 차이** 분석: 연구용 vs 실제 임베딩의 거리 히스토그램
- 거리 분포 차이가 카디널리티 추정에 미치는 영향 정량화

### 산출물
- 연구용 vs 실제 임베딩 거리 분포 비교 시각화
- 데이터셋별 Exqutor 효과 차이 표
- "어떤 임베딩 모델에서 Exqutor가 더 효과적인가"에 대한 분석

### 난이도/현실성
- **난이도**: 중 (임베딩 생성 + 데이터 로딩 필요)
- **강점**: 논문의 외적 타당성(external validity) 검증, 실무 관련성 매우 높음
- **약점**: 임베딩 생성에 API 비용 또는 GPU 시간 필요 (but sentence-transformers는 로컬에서 가능)

## G. HNSW 이외 인덱스(IVFFlat, DiskANN 등) 확장 검증

### 논문의 빈자리
Exqutor의 ECQO는 **HNSW 인덱스의 결정론적 특성**에 의존한다. pgvector가 지원하는 IVFFlat 인덱스에서도 ECQO가 유효한지, 또는 IVFFlat의 비결정론적 특성(nprobe에 따라 결과 변동)이 문제를 일으키는지 검증이 필요하다.

### 실험 아이디어
- 같은 데이터에 HNSW와 IVFFlat 인덱스를 각각 구축
- 동일 쿼리에 대해 ECQO 적용 시:
  - HNSW: 결정론적 결과 → 캐시 재사용 정확
  - IVFFlat: nprobe 값에 따른 결과 변동 → 캐시와 실제 실행 결과 불일치 가능성
- 인덱스 파라미터(ef_search, nprobe) 변화에 따른 카디널리티 변동 폭 측정
- DiskANN(대규모 데이터용)에서의 적용 가능성 이론적 검토

### 산출물
- HNSW vs IVFFlat ECQO 적용 비교표
- 인덱스 파라미터 vs 카디널리티 변동 그래프
- "ECQO가 유효한 인덱스 조건"에 대한 가이드라인

### 난이도/현실성
- **난이도**: 중~상 (IVFFlat의 내부 동작 이해 필요)
- **강점**: Exqutor의 일반화 가능성을 직접 테스트
- **약점**: IVFFlat에서 range query 지원이 제한적일 수 있음

## H. 동적 데이터(INSERT/UPDATE) 환경에서의 카디널리티 추정

### 논문의 빈자리
Exqutor 실험은 **정적 데이터**에서만 수행. 실제 시스템에서는 데이터가 지속적으로 추가/수정되므로:
- HNSW 인덱스가 업데이트될 때 ECQO 결과가 달라질 수 있음
- 적응적 샘플링의 모멘텀 기반 조정이 데이터 분포 변화를 따라잡는지 불확실

### 실험 아이디어
- 초기 데이터 로딩 후 점진적으로 데이터 추가 (10%씩)
- 각 단계에서 ECQO 카디널리티 vs 실제 카디널리티 비교
- 인덱스 리빌드 전/후 비교
- 적응적 샘플링이 분포 변화(distribution drift)에 얼마나 빠르게 적응하는지 측정

### 산출물
- 데이터 증가량 vs 카디널리티 추정 오차 그래프
- 인덱스 리빌드 빈도에 대한 권장 사항
- 분포 드리프트 적응 속도 분석

### 난이도/현실성
- **난이도**: 중~상 (INSERT + 인덱스 업데이트 시간이 오래 걸릴 수 있음)
- **강점**: 운영 환경 적용 시 반드시 고려해야 할 문제
- **약점**: 실험 시간이 길어질 수 있음, Exqutor 코드 수정 없이 관찰만 가능

## I. 멀티 벡터 조인 시나리오 심화

### 논문의 빈자리
Exqutor는 멀티 벡터 쿼리(Figure 8, 9)를 테스트했지만, **두 테이블에 각 1개씩 벡터 컬럼**인 단순 시나리오만 다룸. 실무에서는:
- 같은 테이블에 이미지 벡터 + 텍스트 벡터 (멀티모달)
- 3개 이상 테이블의 벡터 조인
- 벡터 간 크로스 모달 유사도 비교

### 실험 아이디어
- partsupp 테이블에 이미지 + 텍스트 벡터를 동시 저장
- "이미지가 비슷하면서 텍스트 설명도 비슷한 부품 찾기" 같은 멀티 벡터 조건 쿼리
- 벡터 조건이 2개일 때 카디널리티 추정이 어떻게 동작하는지 관찰
- 벡터 조건 간 상관관계(이미지 유사 ↔ 텍스트 유사)가 카디널리티 추정에 미치는 영향

### 산출물
- 멀티 벡터 시나리오별 Q-error 비교
- 벡터 조건 수 vs 실행 시간 스케일링 곡선

### 난이도/현실성
- **난이도**: 중
- **강점**: RAG 시스템의 멀티모달 트렌드와 맞닿아 있음
- **약점**: C번(복합 필터)과 겹치는 부분 있음

## J. 적응적 샘플링 알고리즘 변형 실험

### 논문의 빈자리
Exqutor의 적응적 샘플링은 모멘텀 기반(m=0.9) 단일 전략만 사용. 다른 적응 전략과의 비교가 없다.

### 실험 아이디어
- Exqutor의 모멘텀 기반 방식 vs 대안 비교:
  - **고정 샘플링** (baseline): 항상 385행
  - **단순 비례 조정**: Q-error에 비례해서 바로 조정 (모멘텀 없음)
  - **배치 기반**: 최근 N개 쿼리의 평균 Q-error로 조정
  - **Bayesian 방식**: 사전 분포 + 관측으로 최적 샘플 크기 추론
- 수렴 속도, 안정성, 최종 Q-error 비교

### 산출물
- 샘플링 전략별 Q-error 수렴 곡선
- 전략별 오버헤드(샘플링 시간) 비교

### 난이도/현실성
- **난이도**: 상 (Exqutor 소스 코드 수정 필요)
- **강점**: 알고리즘적 기여가 될 수 있음
- **약점**: 코드 수정 난이도가 높고, ECQO에 비해 효과 차이가 작을 수 있음 (논문에서 1.2~3.2배 → 적응적이 추가로 1.4배 수준)

## K. 벡터 통계 히스토그램 구축 가능성 탐색

### 논문의 빈자리
[20]번 레퍼런스(PostgreSQL 한계 논문)에서 지적한 것처럼, PostgreSQL은 벡터 컬럼에 대한 통계 정보(히스토그램)를 구축하지 못한다. 만약 벡터 거리 분포에 대한 히스토그램을 미리 구축해둘 수 있다면, ECQO처럼 매번 인덱스를 탐색하지 않아도 카디널리티를 추정할 수 있을지 모른다.

### 실험 아이디어
- "앵커 벡터" N개를 선정 (예: k-means 클러스터 센트로이드)
- 각 앵커에 대해 전체 데이터의 거리 분포 히스토그램을 미리 계산
- 새 쿼리 벡터가 들어오면, 가장 가까운 앵커의 히스토그램으로 카디널리티 추정
- ECQO vs 히스토그램 추정 정확도 비교
- 앵커 수(N) vs 추정 정확도 트레이드오프

### 산출물
- 앵커 수 vs Q-error 그래프
- 히스토그램 구축 시간 vs ECQO 쿼리당 오버헤드 비교
- "히스토그램이 ECQO를 대체할 수 있는가?" 에 대한 결론

### 난이도/현실성
- **난이도**: 상 (구현 필요, 통계학적 분석 필요)
- **강점**: 가장 참신한 방향, 새로운 기법 제안에 가까움
- **약점**: 구현 복잡도가 높고, 결과가 "ECQO가 더 나음"으로 나올 가능성도 있음 → 그래도 부정적 결과 자체가 학술적 가치

## L. PostgreSQL 내부 한계와 Exqutor 상호작용 분석

### 논문의 빈자리
[20]번 레퍼런스가 밝힌 PostgreSQL의 5가지 한계(버퍼 풀 오버헤드, MVCC 오버헤드, 공간 증폭, 인덱스 구축 시간, 쿼리 최적화 한계) 중 Exqutor는 5번째만 해결. 나머지 4개가 Exqutor의 효과를 제한하는지, 즉 **카디널리티를 맞춰도 다른 병목 때문에 성능이 안 나오는 경우**가 있는지 확인이 필요하다.

### 실험 아이디어
- 동일 쿼리를 pgvector와 Faiss(순수 벡터 검색)에서 각각 실행
- Exqutor 적용 후에도 Faiss보다 느린 부분 분석:
  - 버퍼 풀 래치 경합 (perf 도구로 측정)
  - MVCC 오버헤드 (pg_stat 확인)
  - 인덱스 크기 비교
- "Exqutor가 최적 계획을 선택했는데도 느린" 경우의 원인 분류

### 산출물
- pgvector+Exqutor vs Faiss 성능 갭 분석
- 병목 원인 분류표 (카디널리티 문제 vs 시스템 한계)
- "Exqutor 이후 다음 최적화 타겟"에 대한 분석

### 난이도/현실성
- **난이도**: 상 (시스템 레벨 프로파일링 필요)
- **강점**: 매우 심층적인 분석, 논문 후속 연구의 로드맵 제시
- **약점**: 시스템 내부 지식 필요, 학부 수준에서 어려울 수 있음

## 추천 조합

### 조합 1: "Exqutor 효과의 경계와 한계" (가장 현실적)

```
B(선택도 Sweep) → A(비용 모델 검증) → D(Top-k vs Range)
                                    → E(필터 순서)
```

- B가 baseline 확립, A가 핵심 실험, D·E가 부가 실험
- **스토리**: "Exqutor가 카디널리티를 맞춰도 옵티마이저가 틀리는 경우가 있다 → 비용 모델 보정이 필요하다"
- 4월: B + 환경 구축 / 5월: A + D / 6월: E + 종합

### 조합 2: "실무 환경 검증" (실용적 가치 중심)

```
B(선택도 Sweep) → C(복합 필터) → F(실제 임베딩)
                              → D(Top-k vs Range)
```

- **스토리**: "Exqutor는 연구용 벤치마크에서 잘 되지만, 실제 RAG 환경의 복합 쿼리에서도 효과적인가?"
- 4월: B + F(임베딩 생성) / 5월: C / 6월: D + 종합

### 조합 3: "새로운 기법 제안" (가장 도전적)

```
B(선택도 Sweep) → K(벡터 히스토그램) → A(비용 모델과 통합)
```

- **스토리**: "ECQO는 효과적이지만 인덱스 필수 → 인덱스 없이도 빠르게 카디널리티를 추정하는 히스토그램 기법 제안"
- 4월: B + K 설계 / 5월: K 구현 + 실험 / 6월: A 통합 + 종합
- 리스크가 크지만 성공 시 가장 높은 학술적 가치

### 조합 4: "팀 내 아이디어 발전" (팀 동기 부여 최적)

```
B(선택도 Sweep) → E(필터 순서: 재현 아이디어)
                → C(복합 필터)
                → A(비용 모델)
```

- **스토리**: "벡터+관계형 복합 쿼리에서 필터 적용 순서가 성능에 미치는 영향 분석 → 최적 순서 가이드라인 제안"
- 재현이의 아이디어를 중심축으로 발전

## 토의 포인트

팀 미팅에서 아래 질문들을 논의하면 방향이 좁혀질 것:

1. **우리가 쓸 수 있는 환경은?** 연구실 서버를 빌릴 수 있는지, 각자 로컬에서만 돌려야 하는지에 따라 가능한 실험 규모가 달라짐
2. **Exqutor 코드를 직접 수정할 의향이 있는가?** 수정 없이 SQL 수준 실험만 한다면 A-F가 현실적, 수정까지 한다면 J-K도 가능
3. **연구제안서의 novelty를 어디서 가져올 것인가?** 단순 재현/검증(B,D)인지, 새로운 실험 설계(A,C,E)인지, 기법 제안(K)인지
4. **2명×2그룹 분담은 어떻게?** 환경구축+실험 vs 분석+문서? 또는 방향별 분담?
5. **DB 환경을 직접 구축해야 한다면** — TPC-H SF10 정도가 로컬에서 현실적. SF100은 서버 필요
