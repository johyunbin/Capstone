## 1. query group key 생성 (§17.1)

### 1.1 입력

query 객체의 메타데이터. 분포 사전 지식이 아니며, query optimizer가 planning 시점에 이미 가지고 있는 정보.

### 1.2 출력

6-tuple group key. 같은 group은 “유사 query”로 묶여 prior accumulation 단위가 된다.

### 1.3 의사코드

```python
def make_group_key(query) -> tuple:
    """
    query metadata로부터 6-tuple group key 생성.
    
    구성 요소:
      table_id              — 어느 table을 대상으로 하는지
      vector_column         — 어느 vector column인지
      distance_metric       — L2 / IP / cosine 등
      threshold_bucket      — distance threshold를 bucketize한 값
      template_id           — query template (예: TPC-H Q3 변형 등)
      scalar_predicates     — scalar predicate signature (정규화된 형태)
    """
    return (
        query.table_id,
        query.vector_column,
        query.distance_metric,
        bucketize_threshold(query.threshold),
        query.template_id,
        normalize_scalar_predicates(query.scalar_predicates),
    )
```

### 1.4 핵심 설계 선택

threshold bucket·template_id·scalar_predicate_signature 세 축이 group key의 핵심이다. 분포 사전 지식 없이 query metadata만으로 prior accumulation 단위를 정의한다 — vector 자체의 임베딩 값이나 데이터 분포는 사용하지 않는다.

`bucketize_threshold`는 distance threshold의 연속값을 이산화한다(예: log-scale bin 또는 dataset별 quantile). 같은 bucket 안 query는 “비슷한 selectivity 영역”으로 가정.

`normalize_scalar_predicates`는 scalar predicate(WHERE 절의 비-vector 조건들)를 정규화 한다 — 예: `o_orderdate BETWEEN '2024-01-01' AND '2024-12-31'`을 `o_orderdate IN <yearly_range>`로 축약. 같은 정규화 결과 = 같은 signature.

## 2. EBQASState 객체 (§17.2)

### 2.1 역할

query group 하나당 유지하는 state. EB-QAS prior 정보의 보관 단위.

### 2.2 필드

```python
class EBQASState:
    def __init__(self):
        self.alpha = 1.0           # Beta prior α
        self.beta = 1.0            # Beta prior β
        self.kappa = 2.0           # α + β (prior strength)
        self.mu = 0.5              # α / (α + β) (prior mean)
        self.n_cap = 385           # max sample budget (Exqutor B1 N=385 기본)
        self.mismatch_count = 0    # prior mismatch reset 발동 횟수 (로그용)
```

### 2.3 초기값 합리화

`Beta(1,1)`로 시작하는 것은 uniform prior — “아무것도 모름”. `Beta(0.5,0.5)`(Jeffreys prior)도 conservative 선택지(정본 anchor §5.3 carry).

`n_cap = 385`는 Exqutor §V-B `N=385`(95% confidence·5% margin·P̂=0.5)와 일치 — EB-QAS는 Exqutor outer controller와 결합 가능(§10.5)하므로 시작은 같은 cap.

`mismatch_count`는 운영 로그용 — 단순 카운터, 활성화 후 figure·summary에서 EB-QAS-safe vs EB-QAS-unsafe 비교에 사용.

### 2.4 직렬화 (선택)

cell·group별 state를 JSON으로 직렬화하면 long-running workload·다음 trial로 carry 가능. 본 trial 단위 실험에서는 in-memory dict로 유지.

## 3. query-time estimation (§17.3)

### 3.1 입력·출력

**입력**:
- `table` — table 객체 (row count·vector access)
- `query` — query 객체 (vector·threshold)
- `state` — EBQASState (해당 group의 prior)
- `params` — EBQASParams (batch_size·τ·n_min 등)

**출력 dict**:
- `estimated_cardinality` — C_hat
- `sample_size` — 실제 사용된 sample 수
- `hits` — sample 중 predicate 만족 row 수
- `posterior_alpha`·`posterior_beta` — 사후 분포 parameter
- `posterior_q_risk` — Q_post = max(p̂/L, U/p̂)
- `early_stopped` — n_cap 도달 전 stop했는지 여부

### 3.2 의사코드

```python
def ebqas_estimate(table, query, state, params):
    """
    EB-QAS query-time cardinality estimation.

    동작:
      1. batch_size 단위로 uniform random sample
      2. 각 sample row의 predicate 만족 여부 계산
      3. 누적 hits로 posterior 갱신
      4. posterior Q-risk 또는 n_cap 도달 시 stop
    """
    N = table.row_count
    n = 0
    s = 0

    while True:
        # 1. uniform random sample (without replacement, batch_size 단위)
        rows = uniform_sample(table, params.batch_size)

        # 2. predicate 만족 여부
        hits = 0
        for row in rows:
            if distance(row.vector, query.vector) < query.threshold:
                hits += 1

        # 3. posterior parameter 갱신
        n += params.batch_size
        s += hits
        a_post = state.alpha + s
        b_post = state.beta + n - s

        # 4. posterior mean
        p_hat = a_post / (a_post + b_post)
        c_hat = N * p_hat

        # 5. posterior credible interval (95% 기본)
        L, U = beta_credible_interval(a_post, b_post, confidence=0.95)
        L = max(L, 1.0 / (N * 10.0))  # division by zero 방지

        # 6. posterior Q-risk
        q_post = max(p_hat / L, U / p_hat)

        # 7. stop 조건
        if n >= params.n_min and q_post <= params.q_target:
            break   # posterior 충분히 안정 → early stop
        if n >= state.n_cap:
            break   # outer cap 도달

    return {
        "estimated_cardinality": c_hat,
        "sample_size": n,
        "hits": s,
        "posterior_alpha": a_post,
        "posterior_beta": b_post,
        "posterior_q_risk": q_post,
        "early_stopped": n < state.n_cap,
    }
```

### 3.3 posterior Q-risk 직관 (§10.3 carry)

`Q_post = max(p̂ / L, U / p̂)`는 posterior 95% credible interval `[L, U]` 안에서 estimate가 최악 몇 배 틀릴 수 있는지 측정. 작을수록 estimate 안정.

- `Q_post ≤ 1.3` → estimate 안정, 멈춤
- `Q_post > 1.3` → 더 sample, batch 추가

### 3.4 batch_size·n_min·n_cap 조정 가이드

- batch_size 16·32·64 권장. 작을수록 stop 해상도 ↑, overhead ↑.
- n_min은 batch_size 2~4 배 권장(early stop 발동 전 최소 sample 보장).
- n_cap은 B1 adaptive sample size 또는 385·512·1024.

### 3.5 환각 회피

- p̂가 0이 되어도(s=0인 batch만 누적된 경우) Beta prior `(α+s, β+n−s)`는 0으로 붕괴 X — prior가 hit 1건 정보를 carry. zero-hit collapse 완화(H2).
- L=0이면 Q_post가 발산. L에 floor(`1/(10N)` 등) 적용 — overflow 방지.

## 4. after-execution update (§17.4)

### 4.1 역할

query 실행이 끝난 뒤 true cardinality를 얻어 다음 query를 위한 group prior를 갱신. **현재 query에는 사용하지 않음** — 다음 query 이후만 영향.

### 4.2 의사코드

```python
def update_after_execution(state, true_cardinality, table_size, posterior_info, params):
    """
    EB-QAS after-execution update.

    동작:
      1. true cardinality로 p_true 계산
      2. p_true가 prior credible interval(99%) 밖이면 mismatch — κ를 γ배 감쇠
      3. empirical-Bayes update — κ는 ρ-decay + w 추가, μ는 weighted average
      4. α·β 재계산
    """
    p_true = true_cardinality / table_size

    # 1. prior mismatch 감지 (99% credible interval 기준 — strict)
    L_prior, U_prior = beta_credible_interval(
        state.alpha, state.beta, confidence=0.99
    )

    if p_true < L_prior or p_true > U_prior:
        # 잘못된 prior — κ를 γ배 감쇠해서 다음 query의 prior 영향 약화
        state.kappa *= params.gamma
        state.mismatch_count += 1
        state.alpha = state.mu * state.kappa
        state.beta = (1.0 - state.mu) * state.kappa

    # 2. empirical-Bayes update (정상 흐름)
    new_kappa = min(
        params.kappa_max,
        params.rho * state.kappa + params.w
    )

    new_mu = (
        params.rho * state.kappa * state.mu + params.w * p_true
    ) / (
        params.rho * state.kappa + params.w
    )

    # 3. 갱신
    state.kappa = new_kappa
    state.mu = min(max(new_mu, 1e-9), 1.0 - 1e-9)  # 0·1 boundary 안전
    state.alpha = state.mu * state.kappa
    state.beta = (1.0 - state.mu) * state.kappa

    # 4. (선택) Exqutor-style outer cap update
    # q_error = max(c_hat / true_cardinality, true_cardinality / c_hat)
    # state.n_cap = update_n_cap_with_momentum_lr(state.n_cap, q_error)
```

### 4.3 mismatch reset 식 직관

- prior credible interval(99%)이 p_true를 포함하지 못함 = prior가 명백히 틀림.
- κ를 `γ=0.5` 배로 감쇠 → 다음 query에서 prior weight ↓, current sample weight ↑.
- mismatch가 반복되면 κ는 계속 작아져 결국 B1 동작에 가까워짐(fallback).
- mismatch_count 로깅으로 운영 모니터링(어떤 group이 자주 mismatch 일으키는지 확인).

### 4.4 empirical-Bayes update 식 (§10.4 carry)

- κ 갱신: `κ ← min(κ_max, ρ·κ + w)` — ρ-decay로 오래된 정보 가중치 감소, w로 새 query 정보 추가, κ_max로 상한.
- μ 갱신: weighted average `μ ← (ρ·κ·μ + w·p_true) / (ρ·κ + w)`.
- α·β는 항상 `μ·κ`·`(1−μ)·κ`로 재계산 — Beta parameterization 일관.

### 4.5 권장 hyperparam (§16 carry)

- ρ = 0.95 (decay)
- w = 10 (new query weight)
- κ_max = 100 (default), 50~200 사이 권장
- γ = 0.5 (mismatch reset 감쇠 — 0.25 ~ 0.5)

## 5. 4 룰 (§18.1~18.4)

### 5.1 double counting 금지 (§18.1)

현재 query sample을 prior와 likelihood 양쪽에 사용하면 **같은 증거를 두 번** 사용한 것 — posterior가 wrongly tight해진다.

**올바른 순서**:
- 이전 query 1 ~ t−1의 true cardinality → prior(`update_after_execution`)
- 현재 query t의 sample → likelihood(`ebqas_estimate`)
- prior × likelihood → posterior
- 현재 query t 실행 후 → 다음 query t+1 이후 prior에 반영(`update_after_execution`)

**금지 패턴**:
- 현재 query sample로 prior를 update한 뒤 같은 sample로 likelihood 계산
- 한 query 내부에서 batch별 prior update + likelihood 동시 — batch는 누적 sample(s, n)으로만 likelihood 계산, prior는 query 시작 시점 state 사용

### 5.2 true cardinality 사용 시점 (§18.2)

- **planning time**: prior + current sample만 사용. true cardinality 사용 금지.
- **execution after**: true cardinality로 state update — 다음 query에만 영향.

이 룰은 5/23 평결 §A.4(paired 비교 통제)와 정본 anchor §B.3(leakage 방지)와 일관. 실험 B(online protocol)에서 critical.

### 5.3 group key 세밀도 하한 (§18.3) — 너무 세밀하면 X

**나쁜 예**:
- group key에 query vector hash를 그대로 포함 → 거의 매 query가 새 group → 모두 cold-start, history 누적 안 됨.
- threshold를 bucket 없이 raw float로 사용.

**좋은 예**:
- threshold bucket(log-scale 또는 dataset quantile)
- template_id (TPC-H Q3 변형 등의 정형 query template)
- scalar predicate signature (정규화된 형태)

### 5.4 group key 세밀도 상한 (§18.4) — 너무 넓으면 X

**나쁜 예**:
- 모든 DEEP query를 한 group으로 묶음 → sel=0.001과 sel=0.10이 섞여 prior 왜곡.
- dataset만 사용하고 threshold·template 무시.

**좋은 예**:
- dataset + threshold_bucket + template_id + predicate_signature 조합.
- 같은 group 안 query는 selectivity가 ±x배 안에 머무는지 사후 검증.

### 5.5 룰 위반 시 안전장치 (§10·§C carry)

§5.3·§5.4를 위반(group key 부적절)해도 EB-QAS-safe(κ cap·decay·mismatch reset)는 prior 영향을 감쇠해 B1 수준으로 fallback. 실험 C(prior mismatch stress)에서 입증.

§5.1·§5.2 위반은 통계적으로 fundamental error — fallback 없음. 본 spec은 measure_ebqas 구현 시 §18.1·§18.2를 **invariant**로 명시(assert·test).

## 7. 환각 회피·평결 호환성 (carry)

본 의사코드는 5/23 감사 평결 4축과 일관:

- **분포 사전 지식 X**: 의사코드 어디서도 vector 분포·CDF·clustering·density map 사용 X. 입력은 query metadata + uniform random sample + 이전 query의 true cardinality(execution 후)뿐.
- **CaseB식 평균 X**: posterior mean은 prior mean과 sample proportion의 가중평균이지 두 독립 추정량의 평균이 아님(§7 carry).
- **latency objective X**: 의사코드 내 latency 측정 항목 없음 — planning time cardinality estimate만 산출. latency는 실험 D에서 별도 평가.
- **method library X**: posterior mean 한 줄 + Beta 분포 update — method paradigm(P1~P10) 어디에도 의존 X.

“EB-QAS가 B1보다 낫다” 단언 X — 본 spec은 측정 결과 평가의 토대일 뿐.
