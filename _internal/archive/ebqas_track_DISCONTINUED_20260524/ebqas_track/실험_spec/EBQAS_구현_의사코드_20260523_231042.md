## 1. query group key 생성 (§17.1) — carry (222815와 동일)

### 1.1 입력

query 객체의 메타데이터. 분포 사전 지식이 아니며, query optimizer가 planning 시점에 이미 가지고 있는 정보.

### 1.2 출력

6-tuple group key. 같은 group은 "유사 query"로 묶여 prior accumulation 단위가 된다.

### 1.3 의사코드

```python
def make_group_key(query) -> tuple:
    """
    query metadata로부터 6-tuple group key 생성.

    구성 요소:
      table_id              — 어느 table을 대상으로 하는지
      vector_column         — 어느 vector column인지
      distance_metric       — L2 / IP / cosine 등
      threshold_bucket      — distance threshold를 log-scale bucketize한 값
      template_id           — query template (예: TPC-H Q3 변형 등)
      scalar_predicates     — scalar predicate signature (정규화된 형태)
    """
    return (
        query.table_id,
        query.vector_column,
        query.distance_metric,
        bucketize_threshold(query.threshold),
        query.template_id,
        normalize_scalar_predicates(query.scalar_predicates),
    )
```

### 1.4 핵심 설계 선택 — carry

threshold bucket·template_id·scalar_predicate_signature 세 축이 group key의 핵심. 분포 사전 지식 없이 query metadata만으로 prior accumulation 단위 정의. vector 자체 임베딩 값이나 데이터 분포 사용 X.

본 신규 spec에서 `bucketize_threshold`는 **log-scale D bucket** (default) 또는 **train-only quantile** (option)로 명시한다 — dataset 전체 quantile 사용은 leakage 위험. 상세는 실험 B outline 신규 파일(`EBQAS_실험BCDE_outline_<HHMMSS>.md` §1.2) carry.

`normalize_scalar_predicates`는 scalar predicate(WHERE 절의 비-vector 조건)를 정규화. 같은 정규화 결과 = 같은 signature.

## 2. EBQASState 객체 (§17.2) — patch

### 2.1 역할 — carry

query group 하나당 유지하는 state. EB-QAS prior 정보의 보관 단위.

### 2.2 필드 (4 필드 신규 추가)

```python
class EBQASState:
    def __init__(self):
        # 기본 prior 정보 (222815 carry)
        self.alpha = 1.0           # Beta prior α
        self.beta = 1.0            # Beta prior β
        self.kappa = 2.0           # α + β (prior strength)
        self.mu = 0.5              # α / (α + β) (prior mean)
        self.n_cap = 385           # max sample budget
        self.mismatch_count = 0    # 누적 mismatch reset 발동 횟수

        # ★ 신규 (본 spec patch) — explicit mode switch용
        self.prior_mode = "history"        # "history" | "no_history"
        self.consecutive_mismatch = 0      # 연속 mismatch 카운터 (회복 시 0으로 reset)
        self.stable_query_count = 0        # 연속 stable query 카운터 (mismatch 시 0)
        self.early_stop = True             # posterior Q-risk 기반 조기 종료 활성 여부
```

### 2.3 초기값 합리화 — carry + 신규

`Beta(1,1)`로 시작하는 것은 uniform prior — "아무것도 모름". `Beta(0.5,0.5)`(Jeffreys prior)도 conservative 선택지.

`n_cap = 385`는 Exqutor §V-B `N=385`(95% confidence·5% margin·P̂=0.5)와 일치 — EB-QAS는 Exqutor outer controller와 결합 가능(§10.5)하므로 시작은 같은 cap.

`mismatch_count`는 운영 로그용 — 단순 카운터. 본 spec patch 후 `consecutive_mismatch`(현재 mismatch streak)와 분리: `mismatch_count`는 cell·group별 누적, `consecutive_mismatch`는 streak.

`prior_mode = "history"`: empirical-Bayes prior 적극 사용. `"no_history"`로 switch 시 Beta(1,1) base + B1 동작.

`early_stop = True`: 정상 흐름. `False`로 switch 시 n_cap까지 무조건 sampling (B1 cap fallback).

### 2.4 직렬화 (선택) — carry

cell·group별 state를 JSON으로 직렬화하면 long-running workload·다음 trial로 carry 가능. 본 trial 단위 실험에서는 in-memory dict로 유지.

## 3. query-time estimation (§17.3) — patch

### 3.1 입력·출력 — carry + 신규

**입력**:
- `table` — table 객체 (row count·vector access)
- `query` — query 객체 (vector·threshold)
- `state` — EBQASState (해당 group의 prior, **`prior_mode`·`early_stop` 반영**)
- `params` — EBQASParams (batch_size·τ·n_min 등 + **`q_target`·`n_min`·`q_log_floor`**)

**출력 dict** (222815 carry + 신규 키 2건):
- `estimated_cardinality` — C_hat
- `sample_size` — 실제 사용된 sample 수
- `hits` — sample 중 predicate 만족 row 수
- `posterior_alpha`·`posterior_beta` — 사후 분포 parameter
- **`posterior_q_risk_log`** — logging용 raw Q_post (신규)
- **`posterior_q_risk_stop`** — stop decision용 floor-adjusted Q_post (신규)
- `early_stopped` — n_cap 도달 전 stop했는지 여부
- **`prior_mode_at_query`** — 본 query 시점 `state.prior_mode` 스냅샷 (신규)

### 3.2 의사코드 (Q_post floor 분리 + prior_mode 반영)

```python
def ebqas_estimate(table, query, state, params):
    """
    EB-QAS query-time cardinality estimation.

    patch (본 신규 spec):
      - posterior credible interval L의 floor를 logging용(L_log)과
        stop decision용(L_stop)으로 분리 — Codex (b) finding 3 carry
      - state.early_stop=False 시 n_cap까지 무조건 sampling (B1 cap fallback)
    """
    N = table.row_count
    n = 0
    s = 0

    while True:
        # 1. uniform random sample (without replacement, batch_size 단위)
        rows = uniform_sample(table, params.batch_size)

        # 2. predicate 만족 여부
        hits = 0
        for row in rows:
            if distance(row.vector, query.vector) < query.threshold:
                hits += 1

        # 3. posterior parameter 갱신
        n += params.batch_size
        s += hits
        a_post = state.alpha + s
        b_post = state.beta + n - s

        # 4. posterior mean
        p_hat = a_post / (a_post + b_post)
        c_hat = N * p_hat

        # 5. ★ posterior credible interval (95% 기본) — floor 분리
        L_raw, U_raw = beta_credible_interval(
            a_post, b_post, confidence=0.95
        )
        L_log = max(L_raw, 0.0)                  # logging용 — raw posterior 보존
        L_stop = max(L_raw, 1.0 / (N * 10.0))    # stop decision용 — 발산 방지

        # 6. ★ posterior Q-risk 분리
        q_post_log = (
            max(p_hat / L_log, U_raw / p_hat)
            if L_log > 0 else float("inf")
        )
        q_post_stop = max(p_hat / L_stop, U_raw / p_hat)

        # 7. ★ stop 조건 — state.early_stop 반영
        if (
            state.early_stop
            and n >= params.n_min
            and q_post_stop <= params.q_target
        ):
            break   # posterior 충분히 안정 → early stop
        if n >= state.n_cap:
            break   # outer cap 도달 (early_stop=False 시 유일한 stop 조건)

    return {
        "estimated_cardinality": c_hat,
        "sample_size": n,
        "hits": s,
        "posterior_alpha": a_post,
        "posterior_beta": b_post,
        "posterior_q_risk_log": q_post_log,    # 신규
        "posterior_q_risk_stop": q_post_stop,  # 신규
        "early_stopped": n < state.n_cap,
        "prior_mode_at_query": state.prior_mode,  # 신규
    }
```

### 3.3 posterior Q-risk 직관 (§10.3 carry + Q_post floor 분리)

`Q_post = max(p̂ / L, U / p̂)`는 posterior 95% credible interval `[L, U]` 안에서 estimate가 최악 몇 배 틀릴 수 있는지 측정. 작을수록 estimate 안정.

본 spec patch에서 L은 두 단계 floor를 갖는다.
- **logging용 (`L_log`)**: `max(L_raw, 0)` — posterior 본래 값 보존, `q_post_log`로 운영 모니터링.
- **stop decision용 (`L_stop`)**: `max(L_raw, 1/(10·N))` — `L=0` 시 `Q_post` 발산 방지, `q_post_stop`로만 early stop 판단.

`L_raw = 0`이면 `q_post_log = ∞`로 로깅(early hit가 없는 cold-start 상황 식별). `q_post_stop`은 항상 유한값.

`q_post_stop ≤ 1.3` → estimate 안정, 멈춤. `q_post_stop > 1.3` → 더 sample.

### 3.4 batch_size·n_min·n_cap 조정 가이드 — carry

- batch_size 16·32·64 권장. 작을수록 stop 해상도 ↑, overhead ↑.
- n_min은 batch_size 2~4 배 권장.
- n_cap은 B1 adaptive sample size 또는 385·512·1024.

### 3.5 환각 회피 — carry + 신규

- p̂가 0이 되어도(s=0인 batch만 누적된 경우) Beta prior `(α+s, β+n−s)`는 0으로 붕괴 X — prior가 hit 정보 carry. zero-hit collapse 완화(H2).
- `L_raw=0`은 logging으로만 활용(`q_post_log=∞`), stop decision에는 사용 X — overflow 방지.
- `state.early_stop=False`(no_history fallback) 시 본 함수는 B1과 동일하게 n_cap까지 sampling. posterior mean은 산출하되 stop decision에는 사용 X.

## 4. after-execution update (§17.4) — patch (explicit mode switch)

### 4.1 역할 — carry

query 실행이 끝난 뒤 true cardinality를 얻어 다음 query를 위한 group prior를 갱신. **현재 query에는 사용하지 않음** — 다음 query 이후만 영향.

### 4.2 의사코드 (explicit mode switch 재설계)

```python
def update_after_execution(state, true_cardinality, table_size, posterior_info, params):
    """
    EB-QAS after-execution update.

    patch (본 신규 spec — Codex (b) fail 정정):
      1. mismatch 감지 → consecutive_mismatch 카운트
      2. consecutive_mismatch >= mismatch_n_threshold 시 explicit mode switch
         (prior_mode="no_history", Beta(1,1) reset, early_stop=False, update skip)
      3. stable_query_count >= n_recovery 시 history 회복 옵션
      4. mismatch query에서 w_mismatch 별도 weight 적용
    """
    p_true = true_cardinality / table_size

    # 1. prior mismatch 감지 (99% credible interval 기준 — strict)
    L_prior, U_prior = beta_credible_interval(
        state.alpha, state.beta, confidence=0.99
    )
    mismatch_this_query = (p_true < L_prior) or (p_true > U_prior)

    # 2. ★ streak 카운터 갱신
    if mismatch_this_query:
        state.mismatch_count += 1
        state.consecutive_mismatch += 1
        state.stable_query_count = 0
    else:
        state.consecutive_mismatch = 0
        state.stable_query_count += 1

    # 3. ★ explicit mode switch — 반복 mismatch 시 no_history fallback
    if (
        state.consecutive_mismatch >= params.mismatch_n_threshold
        and state.prior_mode == "history"
    ):
        # B1과 동등 동작으로 fallback
        state.prior_mode = "no_history"
        state.alpha = 1.0
        state.beta = 1.0
        state.kappa = 2.0
        state.mu = 0.5
        state.early_stop = False        # B1 cap까지 무조건 sampling
        # ★ update skip — 잘못된 prior 방향으로 더 끌려가지 않도록
        return

    # 4. ★ recovery — stable workload 감지 시 history 회복 (선택)
    if (
        state.prior_mode == "no_history"
        and state.stable_query_count >= params.n_recovery
    ):
        state.prior_mode = "history"
        state.early_stop = True
        # alpha/beta/kappa는 Beta(1,1) base 그대로 유지하여 누적 재시작

    # 5. ★ empirical-Bayes update — mismatch query에서 w_mismatch 적용
    w_effective = (
        params.w_mismatch if mismatch_this_query else params.w
    )

    new_kappa = min(
        params.kappa_max,
        params.rho * state.kappa + w_effective
    )

    new_mu = (
        params.rho * state.kappa * state.mu
        + w_effective * p_true
    ) / (
        params.rho * state.kappa + w_effective
    )

    # 6. 갱신
    state.kappa = new_kappa
    state.mu = min(max(new_mu, 1e-9), 1.0 - 1e-9)
    state.alpha = state.mu * state.kappa
    state.beta = (1.0 - state.mu) * state.kappa

    # 7. (선택) Exqutor-style outer cap update — carry
    # q_error = max(c_hat / true_cardinality, true_cardinality / c_hat)
    # state.n_cap = update_n_cap_with_momentum_lr(state.n_cap, q_error)
```

### 4.3 mismatch handling fixed-point 분석 (★ Codex (b) fail 정정 근거)

직전 222815 spec(`§4.2`)의 mismatch 처리는 다음과 같았다.

```text
if mismatch:
    state.kappa *= gamma          # κ ← γ·κ
    state.mismatch_count += 1
    state.alpha = state.mu * state.kappa
    state.beta = (1 - state.mu) * state.kappa

# 그 후 무조건 empirical-Bayes update
state.kappa = min(kappa_max, rho * state.kappa + w)
```

mismatch 감지 직후 κ ← γ·κ가 적용되지만, 같은 호출 안에서 곧바로 `κ ← min(κ_max, ρ·(γ·κ) + w)` = `min(κ_max, ρ·γ·κ + w)`가 적용된다. mismatch가 무한 반복되면 κ는 다음 fixed-point로 수렴한다.

```text
κ* = ρ·γ·κ* + w
κ* = w / (1 − ρ·γ)
```

ρ=0.95, γ=0.5, w=10 (default) → κ* ≈ 10 / 0.525 ≈ 19.05. 즉 mismatch가 끝없이 반복되어도 κ는 0이나 2(Beta(1,1) base)로 가지 않고 약 19 근방에 머문다 — prior 영향이 잔존, B1 동작에 가까워지지 않는다. 이는 정본 anchor §10.4에 명시된 "mismatch가 반복되면 κ는 계속 작아져 결국 B1 동작에 가까워진다"는 spec 문장과 모순이며, spec 수준의 알고리즘 동작 반례다.

본 spec patch는 explicit mode switch로 fallback을 알고리즘 동작으로 보장한다.

| 시나리오 | mismatch streak | κ 변화 | 결과 |
|---|---|---|---|
| 1회 mismatch | `consecutive_mismatch=1 < threshold` | `κ ← min(κ_max, ρ·κ + w_mismatch)` (w_mismatch=1 default) | prior 영향 점진 감소 |
| N회 연속 mismatch | `consecutive_mismatch >= threshold` | mode switch → `κ=2, α=β=1, early_stop=False` | B1 cap fallback, prior 영향 0 |
| stable 회복 | `stable_query_count >= n_recovery` | `prior_mode="history"`, `early_stop=True` | history 누적 재시작 (Beta(1,1) base) |

`mismatch_n_threshold = 3` (default) — 3회 연속 mismatch면 fallback. `n_recovery = 20` (default) — 20회 연속 stable 시 history 회복.

### 4.4 empirical-Bayes update 식 (§10.4 carry + w_mismatch)

- κ 갱신: `κ ← min(κ_max, ρ·κ + w_effective)` — `w_effective = w_mismatch if mismatch_this_query else w`. mismatch query는 `w_mismatch` 별도(default 1).
- μ 갱신: weighted average `μ ← (ρ·κ·μ + w_effective·p_true) / (ρ·κ + w_effective)`.
- α·β는 항상 `μ·κ`·`(1−μ)·κ`로 재계산.

### 4.5 권장 hyperparam (§16 carry + 신규)

- ρ = 0.95 (decay)
- w = 10 (new query weight, mismatch 아닐 때)
- **w_mismatch = 1** (신규, mismatch query weight — 잘못된 방향 학습 약화)
- κ_max = 100 (default), 50~200 사이 권장
- γ = 0.5 (mismatch 1회 감쇠 — 본 spec에서는 streak 기반 mode switch가 주된 fallback, γ는 streak 미달 시 점진 감쇠용)
- **mismatch_n_threshold = 3** (신규, fallback 발동 streak)
- **n_recovery = 20** (신규, history 회복 streak)

## 5. 4 룰 (§18.1~18.4) + §5.5 신규 (룰 위반 시 안전장치 보강)

### 5.1 double counting 금지 (§18.1) — carry

현재 query sample을 prior와 likelihood 양쪽에 사용하면 **같은 증거를 두 번** 사용한 것 — posterior가 wrongly tight해진다.

**올바른 순서**:
- 이전 query 1 ~ t−1의 true cardinality → prior(`update_after_execution`)
- 현재 query t의 sample → likelihood(`ebqas_estimate`)
- prior × likelihood → posterior
- 현재 query t 실행 후 → 다음 query t+1 이후 prior에 반영

**금지 패턴**:
- 현재 query sample로 prior를 update한 뒤 같은 sample로 likelihood 계산
- 한 query 내부에서 batch별 prior update + likelihood 동시

### 5.2 true cardinality 사용 시점 (§18.2) — carry

- **planning time**: prior + current sample만 사용. true cardinality 사용 금지.
- **execution after**: true cardinality로 state update — 다음 query에만 영향.

본 룰은 5/23 평결 §A.4(paired 비교 통제)와 정본 anchor §B.3(leakage 방지)와 일관. 실험 B(online protocol)에서 critical.

### 5.3 group key 세밀도 하한 (§18.3) — carry

**나쁜 예**:
- group key에 query vector hash를 그대로 포함 → 거의 매 query가 새 group → 모두 cold-start, history 누적 안 됨.
- threshold를 bucket 없이 raw float로 사용.

**좋은 예**:
- threshold bucket(log-scale 또는 train-only quantile)
- template_id (TPC-H Q3 변형 등의 정형 query template)
- scalar predicate signature (정규화된 형태)

### 5.4 group key 세밀도 상한 (§18.4) — carry

**나쁜 예**:
- 모든 DEEP query를 한 group으로 묶음 → sel=0.001과 sel=0.10이 섞여 prior 왜곡.
- dataset만 사용하고 threshold·template 무시.

**좋은 예**:
- dataset + threshold_bucket + template_id + predicate_signature 조합.
- 같은 group 안 query는 selectivity가 ±x배 안에 머무는지 사후 검증.

### 5.5 룰 위반 시 안전장치 (§10·§C carry) + ★ 본 spec patch

§5.3·§5.4 위반(group key 부적절)으로 prior와 실제 selectivity가 systematic하게 어긋나면, 본 spec patch의 explicit mode switch가 B1 cap fallback을 보장한다. 직전 222815 spec과의 차이는 다음과 같다.

| 위반 시나리오 | 직전 222815 spec 동작 | 본 spec patch 동작 |
|---|---|---|
| 일회성 mismatch | κ ← γ·κ → ρ·κ + w | `w_mismatch` 별도(default 1) — 잘못된 방향 학습 약화 |
| 반복 mismatch | κ → fixed-point ≈ 19 — prior 잔존, B1 fallback 보장 X | **mode switch** → Beta(1,1) reset + early_stop=False → B1 cap fallback |
| workload drift | 같은 group key 안에서 selectivity 변화 시 prior 늦게 update | mismatch streak 감지 → mode switch 후 stable 회복 시 history 재시작 |
| dataset 전체 quantile bucket (leakage) | spec 수준 fallback 없음 | mismatch streak 감지 → mode switch (실험 C에서 입증) |

§5.1·§5.2 위반은 통계적으로 fundamental error — fallback 없음. 본 spec은 measure_ebqas 구현 시 §18.1·§18.2를 **invariant**로 명시(assert·test).

## 7. 환각 회피·평결 호환성 (carry + 본 patch carry)

본 의사코드 patch는 5/23 감사 평결 4축과 일관.

- **분포 사전 지식 X**: 의사코드 어디서도 vector 분포·CDF·clustering·density map 사용 X. 입력은 query metadata + uniform random sample + 이전 query의 true cardinality(execution 후)뿐.
- **CaseB식 평균 X**: posterior mean은 prior mean과 sample proportion의 가중평균이지 두 독립 추정량의 평균이 아님(§7 carry).
- **latency objective X**: 의사코드 내 latency 측정 항목 없음 — planning time cardinality estimate만 산출. latency는 실험 D에서 별도 평가.
- **method library X**: posterior mean 한 줄 + Beta 분포 update — method paradigm(P1~P10) 어디에도 의존 X.

본 patch가 추가로 보장하는 것:
- **mode switch가 fallback을 알고리즘 동작으로 보장** — Codex (b) fail 정정. spec 문장 수준의 "B1 cap fallback"이 실제 동작.
- **w_mismatch로 잘못된 방향 학습 약화** — mismatch query에서 prior가 더 강화되지 않도록.
- **Q_post floor 분리로 logging과 stop decision 분리** — `L=0` 상황을 logging으로만 식별, stop decision은 항상 유한값으로 안정.

"EB-QAS가 B1보다 낫다" 단언 X — 본 spec은 측정 결과 평가의 토대일 뿐. **본 patch 완료가 measure_ebqas 코드 작성 진입 가능 상태를 의미**, launch는 사용자 활성화 결정 시점 별도 세션.
