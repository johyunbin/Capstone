## 1. 본 연구 framing (불변 — 가장 먼저 내재화)

본 연구는 Exqutor 논문(arXiv:2512.09695v2) 재현이 아니라 **표본 선택(sample selection) 단계 하나**의 개입(무작위 Bernoulli → 분포 인지 stratification)이 추정 오차(Q-error)에 미치는 영향을 전 변인에 걸쳐 검증한 완전 실험 — 3-way matched B1(기존)·CaseA(완전 대체, 음성 대조군)·CaseB(결합, 산술평균). 발표물은 코드명(B1/CaseA/CaseB)·"영역" 필러·영어 메타 라벨·수식 노출 금지.

「엔진 적용 검증」 = 오프라인 검증된 카디널리티 추정치(method 13종 결합 = CaseB)를 패치된 PostgreSQL(서버 55435)에 주입해 "추정치 → 실행 계획 → end-to-end latency" 고리를 닫는 실험. 4조건: 기본엔진(baseline) / 베이스라인(B1) / 결합(CaseB×13) / 오라클(true_card).

## 2. 「엔진 적용 검증」 메커니즘 (불변 전제 — 직전 세션 recon 정본)

- **2-pass**: Exqutor 는 실행 시점 2-pass. planner_hook 는 pass-1(기본 selectivity) 만, `ExecutorRun` 훅이 벡터 술어 탐지·재plan 후 pass-2 실행. **순수 EXPLAIN 영원히 pass-1 만 봄** → plan 캡처는 `auto_explain`(`log_format=json`, `client_min_messages=log`).
- **SeqScan 한정 주입**: `check_for_vector_search`(vector.c L643-694) 는 SeqScan 분기에서만 `injected_card` 사용. pkey IndexScan 경로는 주입 skip → 측정마다 `injection_fired` 플래그 기록 필수.
- **세션 셋업**: 모든 세션 `LOAD 'vector'` 필수. plan capture 세션은 `LOAD 'auto_explain'` **먼저** (훅 체인 순서). `SET vector.update_sample_size=off` + `SET plan_cache_mode=force_custom_plan`.
- **테이블 명명**: 서버 전부 `<name>_<sf>` suffix. harness 는 세션마다 임시 VIEW(`partsupp_deep` + base 7종) 생성 → VAQ 템플릿 무수정 실행.
- **latency 측정**: 실쿼리 직접 실행 + `time.perf_counter()`(EXPLAIN ANALYZE 금지). 2-pass 오버헤드 포함 정직값. n_warmup=1 / n_timed=15 / statement_timeout=600s (default). variant 순서는 `random.Random(20260520)` fixed-seed shuffle — 매 rep 마다 16 variant 가 한 번씩 round-robin → exec_ms[i] 는 같은 epoch 의 측정 (paired test 적합).
- **B1 의 est 클램프**: `est_b1=0` 일 때 MIN_INJECT=1.0 (`measure_latency_realengine.py:74,155-156`) — 0 주입 시 plan 비정상 회피. core 4 cell 의 sel=0.001 에서 모든 cell 의 est_b1=0 → B1 의 injected_card_seen=1.0. 이는 측정 오류가 아니라 "Bernoulli 가 sel=0.001 에서 0 추출 → 1.0 클램프 → planner 가 1.0 으로 plan" 의 정직 노출.

### 4.2 plan 회복 — CaseB ×13 vs B1 (plan_signature_v2 정밀)

plan_signature_v2 = `(Node Type, Relation/Index, Join Type)` pre-order tuple. analyze_latency.plan_signature(Node Type only) 보다 강화 — Hash Join build/probe swap·SeqScan↔IndexScan·Sort/GatherMerge 위치 분간.

|---|--:|--:|---|
| qid=0 | **0/4** ★ | 12.8/13 | q3:hilbert_real |
| qid=1 | **4/4** ★ | 12.8/13 | q3:sparse_rp |

★★★ **핵심**:
- **B1 plan 회복 = 7/12 cell (58%)** — qid 의존 fragile. qid=0 에서는 4/4 cell 모두 B1 plan ≠ oracle plan, qid=1 에서는 4/4 cell 모두 회복. D (vector distance threshold) 변동(qid=0 0.8612 vs qid=1 0.9569) 이 planner 의 B1=1.0 클램프 처리 boundary 를 흔드는 듯.
- **CaseB ×13 oracle-align = 148/156 = 94.9%** — qid 무관 robust. q3 cell 에서 1-6 method 의 부분 분리(over-estimate 영향) 외 모두 oracle plan 회복.
- ⭐ **CaseB > B1 의 plan 측면 가치 = plan 회복 robustness**. latency 자체는 둘 다 비슷한 회복 plan 들이라 큰 차이 없음(§4.3) 이지만, 보장된 정확도가 plan 결정의 가장자리 cell 에서 robust 한 oracle plan 회복을 만든다.
- ★ q3 만 정확도 미달 cell 발생 — qid 마다 다른 method (hilbert_real·sparse_rp·6 method split). hilbert_real 의 q_err=1.124 (over-estimate, est=8546>7603) 가 Hash Join 잔존 유도. sparse_rp 도 비슷한 mode.

### 4.4 honest 관찰·해석

- **q3 의 B1 70s outlier 우려는 해소** — prescan 의 plan_duration_ms 가 단발 EXPLAIN(cold cache + plan compilation 포함) 비용이라 실측 15-rep mean(1018ms) 보다 70배 크게 보였음. 측정 자체는 정상.
- **B1 의 est_b1=0 → MIN_INJECT=1.0 클램프** 는 측정 오류 아님 — paper 의 Bernoulli 가 sel=0.001 에서 0 추출 → 1.0 클램프 → planner 의 plan 결정 → 실제 latency 노출. 정직 보고 필요.
- **plan 회복 → 3-7× speedup 의 일관성** — 모든 12 cell 에서 robust. qid 무관·query 무관. core 4 cell 가설 ★ 검증.
- **B1 plan ≠ oracle plan 인 5 cell** (q3/q10/q12 qid=0, q3 qid=2)에서도 latency 는 oracle 과 비슷 — B1 의 sub-optimal Nested Loop chain 도 baseline 의 Hash Join chain 보다는 충분히 빠른 plan. "plan 회복의 안전망" 이 sel=0.001 에서 폭넓다는 honest 관찰.
- **q3 만의 정확도 미달 method 발생** — q3 는 partsupp ⋈ supplier ⋈ ... 의 join 구조가 plan space 가 가장 풍부한 cell. 정확도 영향이 plan 결정에 가장 민감. 다른 3 쿼리(q9·q10·q12)에서는 13/13 모두 align.
- **prescan 의 sel=0.01 saturated 5 cell** 와 sel=0.001 core 4 cell 의 latency 차이는 다른 mechanism — Phase 0 §4.3 의 "B1 만으로도 oracle 플랜 → 2.6~3.5× speedup" 은 plan-saturated cell. sel=0.001 core 4 cell 의 3-7× speedup 은 더 강한 plan 변화. **probe q3 sel0.01 (saturated, 2.6~3.5×) generalize 금지** (직전 handoff 환각 회피 룰 §9 carry).
