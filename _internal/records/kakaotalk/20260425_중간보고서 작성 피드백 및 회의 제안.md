### 2. 조현빈 — 4가지 피드백 (4/25 13:44)

> 외부 일정 중이라 Claude Code 기반으로 분석 후 대신 답변.

1. **ECQO ≠ 근사**. ECQO 는 "Exact" Cardinality 로, 인덱스(HNSW)에 range query 를 실제로 한 번 돌려서 정확한 건수를 얻음(오버헤드 1.88ms). 근사는 Adaptive Sampling 쪽만. 두 방법을 묶어 "근사"라고 쓰면 ECQO 의 강점이 흐릿해짐.
2. **고정 비율 수치 명시 필요**. 논문 Table I 기준 pgvector 33.3% / VBASE 50% / DuckDB 100% 고정. 데이터 분포·임계값과 무관하게 동일한 값이 나오기 때문에 옵티마이저가 잘못된 plan(Full Scan + Hash Join)을 선택해 실행 시간이 최대 4 orders of magnitude(약 10,000배)까지 늘어남. "오차"보다 "고정 비율 가정 자체가 잘못됐고 → plan 이 망가진다"가 정확.
3. **"맹점/성능 손실" 표현 정정**. `vector.c` line 243 의 `if (table_count > 2)` hook 조건에 의해 multi-table join 시나리오에서만 hook 이 활성화됨. 단일 테이블 쿼리는 hook 우회 후 PostgreSQL default selectivity(1/3)로 fall-through. 따라서 "성능 손실"이 아니라 "Adaptive Sampling 이 단일 테이블 vector range query 에 도달하지 못하는 사각지대(blind spot)"로 표현하는 것이 학술적으로 정확하며, 우리 RQ1 의 4 가지 finding(Hook trigger 사각지대 / plan replacement 부작용 / TABLESAMPLE SYSTEM block bias / query feature 사전 식별 불가능성)과도 자연스럽게 연결됨.
4. **RQ3 누락**. 우리 연구는 두 트랙(Distribution-Aware / Distribution-Agnostic)이므로 도입부의 RQ 정의도 RQ1 사각지대 → RQ2 분포 인지 개선 → RQ3 분포 무인지 확장의 3단 구조로 가야 §3 RQ 정의와 일관성이 있음. 중간보고서 시점에서 RQ3 는 설계만 확정된 상태로 보고.

→ 한 문단 재작성 예시까지 제시 (사각지대·design constraint 표현 포함).
