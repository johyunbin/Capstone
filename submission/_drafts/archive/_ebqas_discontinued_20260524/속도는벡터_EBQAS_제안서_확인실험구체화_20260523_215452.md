# EB-QAS: Empirical-Bayesian Q-error-aware Adaptive Sampling 제안서 및 실험 설계안

## 0. 한 줄 요약

본 방법은 Exqutor의 **distribution-unaware Bernoulli Adaptive Sampling**을 대체하기 위한 방법이다. 데이터 분포를 미리 안다고 가정하지 않고, **이전 유사 query/predicate의 실행 결과**를 empirical prior로 저장한 뒤, 현재 query에서 얻은 sampling 결과와 Bayesian하게 결합하여 cardinality를 추정한다. 목표는 **Q-error를 낮추거나 유지하면서 sample 수를 줄이고**, 그 결과 일부 workload에서 latency도 낮추는 것이다.

---

## 1. 문제 배경

Exqutor는 vector index가 없는 VAQ(Vector-Augmented Analytical Query)에서 전체 vector table을 다 scan하지 않고, 일부 row만 sampling하여 vector predicate cardinality를 추정한다. 논문에서는 index가 없을 때 full KNN scan은 planning 단계에서 너무 비싸므로, 작은 subset에 대해 similarity predicate를 평가해 optimizer에 cardinality estimate를 제공한다고 설명한다. Exqutor의 adaptive sampling은 Q-error를 feedback으로 사용하고, momentum-based adjustment와 learning-rate scheduler를 결합해 sample size를 동적으로 조정한다. ([arXiv][1])

현재 Capstone 레포지토리의 기존 실험은 Exqutor §V-B의 sample selection 단계만 바꾼 실험이다. 레포 README 기준으로 B1은 논문 그대로의 Bernoulli Adaptive Sampling, CaseA는 Bernoulli sample을 method sample로 완전 대체, CaseB는 `est_final = (est_B1 + est_method) / 2`인 산술평균 결합이다. ([GitHub][2])

기존 v13 결과에서는 CaseB가 B1 대비 Q-error를 자주 개선했다. 보고서에 따르면 CaseB는 1508개 paired 비교 중 1344개, 즉 89.1%에서 B1보다 낮은 Q-error를 보였고, paired Δ% 중앙값은 −4.38%였다. 하지만 CaseA는 평균적으로 불안정했고, 완전 대체는 negative control로 정리되어 있다. ([GitHub][3])

중요한 점은 latency다. 확장 latency PoC에서는 baseline을 제외한 B1·CaseB·oracle 비교에서 `condition`의 설명력이 거의 0으로 나타났다. 즉 해당 실험 평면에서는 CaseB의 Q-error 개선이 engine latency 개선으로 강하게 연결되지 않았다. ([GitHub][4])

따라서 새 방법의 목표는 다음과 같다.

```text
기존 CaseB:
  B1 Bernoulli estimate + method estimate를 산술평균
  → B1을 대체하지 않음
  → Q-error는 개선될 수 있으나 latency 개선은 제한적

새 방법 EB-QAS:
  B1 Bernoulli Adaptive Sampling 자체를 대체
  → 같은 query stream에서 더 적은 sample로 비슷하거나 더 낮은 Q-error 달성
  → sampling overhead 감소 가능
  → 일부 plan-sensitive query에서 latency 개선 가능
```

## 2. 핵심 제약 조건

이 방법은 다음 제약을 반드시 지킨다.

```text
1. 데이터 분포를 미리 알고 있다고 가정하지 않는다.
2. vector table 전체에 대한 CDF, clustering, density map, histogram을 미리 만든다고 가정하지 않는다.
3. query-time에 무거운 학습 모델이나 clustering을 수행하지 않는다.
4. 사용할 수 있는 정보는 다음뿐이다.
   - 현재 query에서 뽑은 uniform random sample 결과
   - 이전에 실행된 유사 query/predicate의 true cardinality
   - 이전 query의 Q-error
   - query template, threshold bucket, scalar predicate signature 등 query metadata
5. objective는 runtime이 아니다.
   - method objective: posterior Q-error risk + sample budget
   - evaluation metric: Q-error, sample size, sampling overhead, latency
```

이 조건 때문에 이전에 논의했던 “offline distribution-aware stratification” 계열은 본 방법의 핵심이 아니다. 지금 제안하는 방법은 **분포 사전 지식이 없는 history-aware empirical-Bayes sampling**이다.

## 4. 기존 Exqutor Adaptive Sampling과의 차이

| 항목             | Exqutor Adaptive Sampling          | EB-QAS                                |
| -------------- | ---------------------------------- | ------------------------------------- |
| 표본 선택          | uniform Bernoulli random sampling  | uniform Bernoulli random sampling     |
| 분포 사전 지식       | 없음                                 | 없음                                    |
| 과거 정보 사용       | Q-error로 다음 sample size 조절         | 유사 query의 true selectivity를 prior로 누적 |
| state 단위       | 주로 table별 sample size state        | query group별 Beta prior + sample cap  |
| 현재 query 내부 판단 | 정해진 sample size만큼 sampling         | posterior uncertainty를 보고 조기 종료 가능    |
| estimate       | sample proportion 기반               | posterior mean 기반                     |
| 안정화            | momentum + learning-rate scheduler | Exqutor식 outer cap 유지 가능              |
| 핵심 목표          | Q-error와 sampling overhead 균형      | posterior Q-risk와 sample budget 균형    |
| runtime 위치     | 평가 지표                              | 평가 지표                                 |

Exqutor는 이미 강한 baseline이다. 논문상 adaptive sampling은 Q-error feedback, momentum, learning-rate decay를 사용해 sample size를 안정화하고, sample size update는 50 queries마다 trigger된다. 또한 adaptive sampling은 fixed sampling 대비 speedup을 보였고, dataset-specific equilibrium으로 수렴한다고 설명된다. ([arXiv][1])

EB-QAS의 차별점은 sample size smoothing이 아니다. Exqutor가 이미 그 역할을 한다. EB-QAS의 차별점은 **과거 query 결과를 단순히 sample size에만 반영하지 않고, selectivity 자체에 대한 prior belief로 저장한다는 점**이다.

## 5. Bayesian estimation이 적용되는 위치

### 5.1 우리가 추정하려는 값

현재 query의 vector predicate를 다음처럼 둔다.

```sql
distance(v_i, q) < D
```

각 row (i)에 대해 predicate 만족 여부를 다음과 같이 정의한다.

[
Y_i =
\begin{cases}
1 & \text{if } distance(v_i, q) < D \
0 & \text{otherwise}
\end{cases}
]

우리가 알고 싶은 것은 true cardinality (C) 또는 selectivity (p)다.

[
C = \sum_{i=1}^{N} Y_i
]

[
p = \frac{C}{N}
]

여기서:

```text
N = table row 수
C = true cardinality
p = true selectivity
```

---

### 5.2 현재 sample 결과

현재 query에서 uniform random sample (n)개를 뽑았다고 하자.

그중 predicate를 만족한 row 수를 (s)라고 한다.

```text
n = sample size
s = sample hit count
```

그러면 현재 sample 결과는 다음처럼 볼 수 있다.

[
s \mid p,n \sim Binomial(n,p)
]

정확히는 table에서 without replacement로 뽑으면 hypergeometric model이 더 엄밀하다. 하지만 (N)이 크고 (n \ll N)이면 Binomial approximation이 실용적으로 자연스럽다.

---

### 5.3 prior는 무엇인가?

EB-QAS에서 prior는 “데이터 분포를 미리 알고 만든 정보”가 아니다.

prior는 **이전 유사 query/predicate의 실행 결과로부터 온라인으로 누적한 belief**다.

유사 query group (g)를 다음처럼 정의한다.

```text
g = (
  table_id,
  vector_column,
  distance_metric,
  threshold_bucket,
  query_template,
  scalar_predicate_signature
)
```

각 group (g)마다 selectivity prior를 저장한다.

[
p_g \sim Beta(\alpha_g,\beta_g)
]

처음에는 아무것도 모르므로 다음처럼 시작한다.

[
p_g \sim Beta(1,1)
]

또는 조금 더 conservative하게:

[
p_g \sim Beta(0.5,0.5)
]

를 사용할 수 있다.

Empirical Bayes는 prior를 고정된 사전 지식으로 가정하지 않고, 관측된 data에서 prior를 추정하는 접근이다. Efron은 empirical Bayes의 핵심 직관을 “한 case를 추정할 때 다른 관련 관측치들이 그 추정을 도울 수 있다”는 식으로 설명한다.

EB-QAS에서는 다음과 같이 대응된다.

```text
현재 case:
  현재 query의 selectivity p

다른 관련 관측치:
  이전 유사 query들의 true selectivity

prior:
  이전 유사 query 결과로 업데이트된 Beta(α_g, β_g)
```

---

### 5.4 likelihood는 무엇인가?

현재 query에서 (n)개 sample 중 (s)개가 hit였을 때, likelihood는 다음이다.

[
P(s \mid p,n)
=============

\binom{n}{s}p^s(1-p)^{n-s}
]

즉:

```text
p가 true selectivity라고 가정했을 때,
n개 sample 중 s개가 hit로 관측될 확률
```

이것이 likelihood다.

---

### 5.5 posterior는 무엇인가?

Bayes rule은 다음이다.

[
P(p \mid s,n)
=============

\frac{
P(s \mid p,n)P(p)
}{
P(s \mid n)
}
]

여기서:

```text
P(p)          = prior
P(s | p, n)   = likelihood
P(p | s, n)   = posterior
P(s | n)      = evidence, 즉 normalization constant
```

Beta prior와 Binomial likelihood를 결합하면 posterior도 Beta가 된다. Beta-Binomial model에서 posterior parameter는 성공 수와 실패 수를 prior parameter에 더하는 형태가 된다. ([Bayes Rules][5])

구체적으로:

[
p_g \sim Beta(\alpha_g,\beta_g)
]

[
s \mid p_g,n \sim Binomial(n,p_g)
]

이면 posterior는:

[
p_g \mid s,n
\sim
Beta(\alpha_g+s,\beta_g+n-s)
]

---

### 5.6 왜 분모 (P(s \mid n))를 계산식에서 자주 생략하는가?

분모는 다음 적분이다.

[
P(s \mid n)
===========

\int_0^1 P(s \mid p,n)P(p)dp
]

이 값은 posterior가 전체 합 1이 되도록 만드는 normalization constant다.

posterior의 모양을 유도할 때는 (p)에 의존하는 항만 보면 된다.

[
P(p \mid s,n)
\propto
P(s \mid p,n)P(p)
]

여기서 (\propto)는 “비례한다”는 뜻이다.

prior와 likelihood를 곱하면:

[
P(s \mid p,n)P(p)
\propto
p^s(1-p)^{n-s}
\cdot
p^{\alpha_g-1}(1-p)^{\beta_g-1}
]

# [

p^{\alpha_g+s-1}
(1-p)^{\beta_g+n-s-1}
]

이것은 Beta distribution의 형태다. 그래서 posterior가 다음과 같다는 것을 알 수 있다.

[
Beta(\alpha_g+s,\beta_g+n-s)
]

즉 분모를 “없애는” 것이 아니라, posterior 형태를 찾을 때 잠시 생략하고 마지막에는 정규화된 Beta distribution으로 복원하는 것이다.

## 6. posterior mean과 cardinality estimate

posterior가 다음이라고 하자.

[
p_g \mid s,n
\sim
Beta(\alpha_g+s,\beta_g+n-s)
]

posterior mean은:

[
\hat{p}
=======

\frac{\alpha_g+s}
{\alpha_g+\beta_g+n}
]

cardinality estimate는:

[
\hat{C}
=======

# N\hat{p}

N
\frac{\alpha_g+s}
{\alpha_g+\beta_g+n}
]

---

## 7. EB-QAS가 Bayesian인 이유를 직관적으로 보기

[
\mu_g = \frac{\alpha_g}{\alpha_g+\beta_g}
]

[
\kappa_g = \alpha_g+\beta_g
]

라고 두자.

그러면 posterior mean은 다음처럼 다시 쓸 수 있다.

[
\hat{p}
=======

\frac{\kappa_g}{\kappa_g+n}\mu_g
+
\frac{n}{\kappa_g+n}\frac{s}{n}
]

즉:

```text
posterior mean
=
prior mean과 현재 sample proportion의 가중평균
```

여기서:

```text
prior mean μ_g:
  이전 유사 query들이 말해주는 평균 selectivity

sample proportion s/n:
  현재 query sample이 말해주는 selectivity

κ_g:
  prior를 얼마나 강하게 믿을지 나타내는 값

n:
  현재 query에서 실제로 본 sample 수
```

(\kappa_g)가 크면 prior를 더 많이 믿는다.
(n)이 크면 현재 query sample을 더 많이 믿는다.

]

즉:

[
p_g \sim Beta(2,198)

```text
n = 100
```

[

p_g \mid s,n
\sim
Beta(2+0,198+100)

Beta(2,298)
]

posterior mean:

[
\hat{p}
=======

# \frac{2}{300}

# 0.00667

\hat{C}

6,667

하지만 만약 실제로 현재 query selectivity가 10%에 가깝다면, prior가 너무 강해서 underestimation이 생긴다. 그래서 EB-QAS에는 반드시 prior mismatch detection이 필요하다.

## 9. (\kappa)를 무한히 키우면 안 되는 이유

(\kappa_g)는 prior strength다.

[
\hat{p}
=======

\frac{\kappa_g}{\kappa_g+n}\mu_g
+
\frac{n}{\kappa_g+n}\frac{s}{n}
]

(\kappa_g)가 너무 크면 현재 query sample을 거의 무시한다.

예를 들어:

```text
prior mean μ_g = 1%
κ_g = 10,000
current sample n = 500
sample proportion = 5%
```

이면:

[
\hat{p}
=======

\frac{10000}{10500}\times1%
+
\frac{500}{10500}\times5%
]

[
\approx
1.19%
]

현재 sample은 5%라고 강하게 말하고 있는데 posterior는 1.19%에 머문다.

DB 데이터가 변하지 않아도 query vector (q), threshold (D), scalar predicate (F)가 바뀌면 true selectivity는 달라진다.

[
p = p(q,D,F)
]

따라서 동일 query만 반복한다면 (\kappa)를 크게 해도 된다. 그 경우에는 사실 true cardinality를 cache하면 된다. 하지만 “유사 query”는 동일 query가 아니므로 (\kappa)를 제한해야 한다.

권장 안전장치:

```text
κ_max:
  prior strength 상한

decay ρ:
  오래된 query feedback의 영향 감소

mismatch detection:
  현재 sample이 prior와 크게 다르면 κ 감소

fallback:
  history가 부족하거나 mismatch가 반복되면 B1처럼 동작
```

## 10. EB-QAS 알고리즘

### 10.1 유지할 state

query group (g)마다 다음 state를 유지한다.

```text
alpha_g       # Beta prior의 α
beta_g        # Beta prior의 β
mu_g          # alpha_g / (alpha_g + beta_g)
kappa_g       # alpha_g + beta_g
n_cap_g       # Exqutor-style maximum sample budget
mismatch_g    # prior mismatch count
```

초기값 예시:

```text
alpha_g = 1
beta_g = 1
mu_g = 0.5
kappa_g = 2
n_cap_g = 385 또는 Exqutor B1의 현재 adaptive sample size
mismatch_g = 0
```

Exqutor 논문에서는 95% confidence level과 5% margin of error 설정으로 fixed sample size를 산출하고, adaptive sampling은 Q-error feedback으로 sample size를 조절한다. ([arXiv][1])

---

### 10.2 query-time procedure

```text
Input:
  N: table row count
  q: query vector
  D: distance threshold
  g: query group key
  batch_size b
  target posterior Q-risk τ
  max sample budget n_cap_g

Initialize:
  n = 0
  s = 0

Loop:
  1. Uniform random sample b rows.
  2. For each sampled row, compute:
       hit = 1[distance(v_i, q) < D]
  3. Accumulate:
       n = n + b
       s = s + number_of_hits_in_batch

  4. Posterior:
       a_post = alpha_g + s
       b_post = beta_g + n - s

  5. Posterior mean:
       p_hat = a_post / (a_post + b_post)
       C_hat = N * p_hat

  6. Posterior interval:
       [L, U] = Beta credible interval of Beta(a_post, b_post)

  7. Posterior Q-risk:
       Q_post = max(p_hat / L, U / p_hat)

  8. Stop if:
       Q_post <= τ

  9. Stop if:
       n >= n_cap_g

Return:
  C_hat
  n
  posterior state for logging
```

---

### 10.3 posterior Q-risk

Q-error는 다음이다.

[
Q\text{-}error =
\max
\left(
\frac{\hat{C}}{C},
\frac{C}{\hat{C}}
\right)
]

cardinality는 (C=Np)이므로 selectivity 기준으로 봐도 동일하다.

posterior credible interval을:

[
[L,U]
]

라고 하자.

estimate를 (\hat{p})라고 하면 posterior Q-risk를 다음처럼 정의한다.

[
Q_{\text{post}}
===============

\max
\left(
\frac{\hat{p}}{L},
\frac{U}{\hat{p}}
\right)
]

해석:

```text
posterior상 plausible한 selectivity 범위 안에서,
현재 estimate가 최악의 경우 몇 배 틀릴 수 있는가?
```

만약:

```text
Q_post <= 1.3
```

이면 posterior 기준으로 estimate가 충분히 안정적이라고 보고 sampling을 멈춘다.

---

### 10.4 실행 후 update

query 실행이 끝나면 true cardinality를 얻는다.

[
p_{\text{true}} = \frac{C_{\text{true}}}{N}
]

이 값을 다음 query들을 위한 group prior에 반영한다.

먼저 prior mismatch를 확인한다.

```text
if p_true is far outside posterior/prior predictive range:
    kappa_g                  = gamma * kappa_g
    mismatch_g              += 1
    consecutive_mismatch_g  += 1
else:
    consecutive_mismatch_g   = 0
    stable_query_count_g    += 1
```

```text

    # B1 cap fallback — Beta(1,1) reset
    prior_mode_g     = "no_history"
    alpha_g, beta_g  = 1.0, 1.0
    kappa_g, mu_g    = 2.0, 0.5
    early_stop_g     = False
    return   # update skip — 잘못된 prior 방향 학습 차단

if prior_mode_g == "no_history" and stable_query_count_g >= n_recovery:
    # stable workload 회복 시 history 재시작 (선택)
    prior_mode_g     = "history"
    early_stop_g     = True
```

예시:

```text
gamma                = 0.5
mismatch_n_threshold = 3
n_recovery           = 20
w_mismatch           = 1   # mismatch query에서 사용하는 weight (정상 w=10과 별도)
```

그 후 empirical-Bayes update를 한다. mismatch 발생 query에서는 `w_mismatch`, 정상 query에서는 `w`를 사용해 잘못된 방향 학습을 약화시킨다.

[
w_{\text{effective}} =
\begin{cases}
w_{\text{mismatch}} & \text{if mismatch\_this\_query} \\
w & \text{otherwise}
\end{cases}
]

[
\mu_g \leftarrow
\frac{
\rho \kappa_g \mu_g + w_{\text{effective}} \, p_{\text{true}}
}{
\rho \kappa_g + w_{\text{effective}}
}
]

[
\kappa_g \leftarrow
\min(\kappa_{\max}, \rho \kappa_g + w_{\text{effective}})
]

[
\alpha_g \leftarrow \mu_g \kappa_g
]

[
\beta_g \leftarrow (1-\mu_g)\kappa_g
]

권장 초기 hyperparameter:

```text
rho                  = 0.95
w                    = 10            # 정상 query 시 prior update weight
w_mismatch           =  1            # mismatch query 시 별도 weight (Codex (b) 정정)
kappa_max            = 100           # 50~200 권장
gamma                = 0.5           # mismatch 1회 κ 감쇠 (mode switch 미발동 streak 한정)
mismatch_n_threshold =  3            # 연속 mismatch가 이만큼 쌓이면 mode switch
n_recovery           = 20            # 연속 stable이 이만큼 쌓이면 history 회복 옵션
```

### 10.5 Exqutor outer controller와의 결합

EB-QAS는 Exqutor의 momentum/LR scheduler를 완전히 버릴 필요가 없다.

추천 구조는 다음이다.

```text
Outer loop:
  Exqutor-style adaptive controller
  → n_cap_g 또는 base_budget_g를 안정화

Inner loop:
  EB-QAS posterior stopping
  → 현재 query에서 실제로 몇 개 sample할지 결정
```

즉:

```text
Exqutor:
  이번 query는 최대 1000개까지 sampling해라.

EB-QAS:
  posterior Q-risk가 충분히 작으면 128개에서 멈춘다.
  불확실하면 256, 512, ..., 최대 1000개까지 간다.
```

이 구조는 Exqutor의 sample-size stability 장점을 유지하면서, 유사 query history를 더 직접적으로 활용한다.

## 11. 수학적 근거

### 11.1 Bernoulli estimator의 variance

B1의 estimator는 다음이다.

[
\hat{p}_{B1} = \frac{s}{n}
]

이 estimator는 unbiased다.

[
E[\hat{p}_{B1}] = p
]

variance는 대략:

[
Var(\hat{p}_{B1})
=================

\frac{p(1-p)}{n}
]

즉 sample 수 (n)을 늘려야 variance가 줄어든다.

---

### 11.2 EB posterior mean은 shrinkage estimator다

EB-QAS의 posterior mean은:

[
\hat{p}_{EB}
============

\frac{\kappa}{\kappa+n}\mu
+
\frac{n}{\kappa+n}\hat{p}_{B1}
]

즉 B1의 sample proportion을 prior mean (\mu) 쪽으로 당긴다.

이것을 shrinkage라고 한다.

좋은 shrinkage는 noisy estimate를 안정화한다.
나쁜 shrinkage는 현재 query를 과거 평균으로 과도하게 끌고 간다.

---

### 11.3 EB-QAS가 B1보다 좋아지는 조건

현재 true selectivity를 (p)라고 하자.

prior mean과 true selectivity의 차이를:

[
\delta = \mu - p
]

라고 한다.

B1의 MSE는:

[
MSE_{B1}
========

\frac{p(1-p)}{n}
]

EB estimator의 MSE는:

[
MSE_{EB}
========

\frac{
n p(1-p)+\kappa^2(\mu-p)^2
}{
(n+\kappa)^2
}
]

EB-QAS가 B1보다 MSE가 작아지는 조건은 대략 다음이다.

[
(\mu-p)^2
<
p(1-p)
\left(
\frac{1}{n}
+
\frac{2}{\kappa}
\right)
]

해석:

```text
prior mean μ가 현재 query의 true p와 충분히 가까우면 EB-QAS가 좋다.
prior mean μ가 현재 query와 많이 다르면 EB-QAS가 나쁘다.
κ가 너무 크면 틀린 prior의 피해가 커진다.
```

따라서 EB-QAS의 핵심은 “Bayesian이라서 무조건 좋다”가 아니다.

```text
유사 query grouping이 잘 되어 있고,
prior strength를 안전하게 제한할 때
B1보다 좋은 성능을 기대할 수 있다.
```

---

### 11.4 sample 수를 줄일 수 있는 이유

posterior variance는 대략 다음처럼 줄어든다.

[
Var(p \mid data)
\approx
\frac{p(1-p)}{n+\kappa}
]

B1은 현재 query sample (n)만 쓴다.

[
Var_{B1}
\approx
\frac{p(1-p)}{n}
]

EB-QAS는 과거 유사 query history가 (\kappa)만큼의 effective sample처럼 작동한다.

따라서 같은 posterior uncertainty target을 만족하기 위한 현재 query sample 수가 줄어들 수 있다.

[
n_{EB}
\approx
n_{B1} - \kappa
]

물론 이 해석은 prior가 현재 query에 relevant할 때만 유효하다.

---

### 11.5 optional stopping 문제와 confidence sequence

EB-QAS는 current query에서 batch를 조금씩 추가하면서 stop 여부를 판단한다. 이런 sequential stopping에서는 일반 fixed-time confidence interval을 그대로 쓰면 optional stopping 문제가 생길 수 있다.

이를 엄밀하게 보강하려면 confidence sequence를 사용할 수 있다. Confidence sequence는 sampling을 언제 멈추더라도 유효한 time-uniform interval을 제공하기 위한 도구다. 최근 연구에서는 bounded random variable의 mean estimation에서 adaptive stopping과 confidence sequence를 결합하는 방법이 제시되어 있고, sampling without replacement finite population에 대한 confidence sequence 연구도 있다. ([Proceedings of Machine Learning Research][6])

실험 1차 구현에서는 Beta credible interval만 사용해도 된다. 다만 논문/보고서에서 이론적 안전성을 강조하려면 optional variant로 CS-EBQAS를 추가한다.

```text
EB-QAS:
  Beta posterior interval로 stop

CS-EBQAS:
  Beta posterior interval + confidence sequence guard로 stop
```

## 12. 선행 연구 기반 근거

### 12.1 Exqutor와의 직접 연결

Exqutor는 vector index가 없는 VAQ에서 sampling-based cardinality estimation을 사용하고, adaptive sampling으로 sample size를 조절한다. Q-error, momentum, learning-rate scheduler를 결합해 accuracy와 planning overhead의 균형을 맞추는 것이 핵심이다. ([arXiv][1])

EB-QAS는 Exqutor를 대체하되, 기존 강점을 유지한다.

```text
유지:
  uniform random sampling
  Q-error feedback
  adaptive sample cap
  momentum/LR outer controller

추가:
  query-group prior
  posterior uncertainty
  posterior Q-risk stopping
```

---

### 12.2 Empirical Bayes

Empirical Bayes는 prior를 완전히 주관적으로 정하지 않고, 관련 관측치들에서 prior를 추정하는 방법이다. Efron의 overview는 empirical Bayes가 “다른 observation들이 특정 case의 inference를 돕는다”는 아이디어에 기반한다고 설명한다.

EB-QAS에서는 이전 유사 query들이 현재 query의 selectivity 추정을 돕는다.

---

### 12.3 Bayesian cardinality estimation 계열

BayesCard는 Bayesian Network를 cardinality estimation에 적용한 대표 연구다. 다만 BayesCard는 data distribution을 Bayesian Network로 모델링하는 방향이다. ([arXiv][7])

EB-QAS는 BayesCard와 다르다.

```text
BayesCard:
  table distribution model을 학습

EB-QAS:
  table distribution을 미리 모델링하지 않음
  query-history feedback만으로 selectivity prior를 업데이트
```

---

### 12.4 uncertainty-aware cardinality estimation

Fauce는 cardinality estimation에 uncertainty information을 포함하려는 PVLDB 연구다. cardinality estimation은 optimizer가 execution plan을 고르는 데 핵심이며, 복잡한 query에서는 estimation accuracy가 크게 떨어질 수 있다고 설명한다.

EB-QAS도 point estimate만 만들지 않는다.

```text
point estimate:
  C_hat

uncertainty:
  posterior interval
  posterior Q-risk
```

이 uncertainty를 sampling stop decision에 사용한다.

---

### 12.5 Q-error만으로는 부족하다는 근거

Flow-Loss 연구는 모든 cardinality estimate가 query optimization에 똑같이 중요한 것은 아니며, optimizer에 영향을 주는 estimate가 더 중요하다고 주장한다. 해당 논문은 Q-error로 학습한 모델보다 estimation accuracy가 나빠도 query runtime에서는 더 좋은 경우가 있음을 보고한다.

Cardinality Estimation in DBMS benchmark 연구도 real DBMS에서 CardEst method를 평가할 때 end-to-end query time과 estimator inference latency를 함께 봐야 한다고 지적한다. ([VLDB][8])

따라서 EB-QAS 실험은 Q-error만 보면 안 된다.

```text
필수 metric:
  Q-error
  final sample size
  sampling overhead
  latency
  plan change
  injection fired 여부
```

---

## 13. 예상 효과

### 13.1 Q-error 측면

EB-QAS가 특히 좋아질 수 있는 경우:

```text
1. 유사 query/predicate가 반복된다.
2. 같은 threshold bucket에서 selectivity가 안정적이다.
3. low-selectivity query에서 sample hit가 0개인 경우가 많다.
4. Exqutor의 table-level sample size state가 query group별 차이를 충분히 반영하지 못한다.
```

예상 효과:

```text
- median Q-error 감소
- p95 Q-error 감소
- zero-hit로 인한 extreme Q-error 감소
- cold-start에서는 B1과 유사
- history가 쌓이면 B1보다 적은 sample로 유사한 Q-error 달성 가능
```

---

### 13.2 latency 측면

EB-QAS의 objective는 runtime이 아니다. 그러나 latency 개선 가능성은 있다.

가능한 경로:

```text
posterior가 빨리 안정됨
→ current query sample 수 감소
→ distance computation 수 감소
→ sampling overhead 감소
→ 일부 workload에서 planning/overall latency 감소
```

특히 vector dimension이 큰 경우 distance computation 1회의 비용이 크므로 sample 수 감소의 효과가 더 크다. Exqutor도 high-dimensional space에서는 sampling overhead가 distance computation cost 때문에 증가할 수 있다고 한계를 언급한다. ([arXiv][1])

다만 전체 latency 개선은 보장되지 않는다. Capstone latency PoC처럼 cardinality estimate 차이가 plan이나 execution path를 바꾸지 못하면, Q-error 개선이 latency 개선으로 이어지지 않을 수 있다. ([GitHub][4])

따라서 latency 결과는 다음처럼 나누어 봐야 한다.

```text
- 전체 평균 latency
- plan_changed subset
- low-selectivity subset
- high-dimensional subset
- sampling overhead only
- injection_fired=True subset
```

---

## 14. 장점과 단점

### 14.1 장점

```text
1. 분포를 미리 안다는 가정이 없다.
   - uniform random sampling만 사용한다.
   - offline clustering, CDF, histogram이 필요 없다.

2. Exqutor의 feedback을 더 정보량 있게 사용한다.
   - Exqutor: 과거 Q-error → sample size 조정
   - EB-QAS: 과거 true selectivity → prior update

3. low-selectivity zero-hit 문제를 완화한다.
   - sample hit가 0이어도 estimate가 0으로 붕괴하지 않는다.

4. current query에서 조기 종료가 가능하다.
   - posterior Q-risk가 충분히 작으면 n_cap까지 가지 않는다.

5. 기존 레포 실험에 자연스럽게 추가 가능하다.
   - B1, CaseA, CaseB 옆에 EB-QAS mode를 추가하면 된다.

6. 계산 비용이 작다.
   - Beta posterior update는 O(1)이다.
   - 주요 비용은 여전히 vector distance computation이다.
```

---

### 14.2 단점과 위험

```text
1. query group 정의가 어렵다.
   - 너무 넓으면 서로 다른 query가 섞여 prior가 틀린다.
   - 너무 좁으면 history가 부족해 B1과 차이가 없다.

2. prior가 틀리면 B1보다 나빠질 수 있다.
   - 특히 κ가 너무 크면 현재 sample을 무시한다.

3. drift에 취약할 수 있다.
   - workload가 바뀌면 prior가 낡은 정보가 된다.
   - decay와 reset이 필요하다.

4. latency 개선은 조건부다.
   - sample 수를 줄여도 plan이 안 바뀌면 engine latency는 거의 그대로일 수 있다.

5. 실험 설계가 sequential해야 한다.
   - random shuffle 결과에 따라 history가 달라질 수 있다.
   - 여러 seed로 반복해야 한다.
```

# 실험 B. 유사 query 반복 실행 online protocol

## B.1 목적

EB-QAS는 history를 사용한다. 따라서 단발성 query shuffle보다 **유사 query가 반복되는 online workload**에서 장점이 잘 드러난다.

이 실험은 Exqutor adaptive sampling과 공정하게 비교하기 위한 핵심 실험이다. Exqutor도 과거 Q-error로 sample size를 조절하므로, EB-QAS도 같은 query stream에서 과거 feedback을 사용할 수 있게 해야 한다.

---

## B.2 query stream 구성

query group을 다음처럼 정의한다.

```text
g = (
  dataset,
  vector_column,
  distance_metric,
  threshold_bucket,
  query_template,
  scalar_predicate_signature
)
```

각 group마다 query stream을 만든다.

예시:

```text
Group 1:
  DEEP, sel=0.001, query_template=Q1

Group 2:
  DEEP, sel=0.01, query_template=Q1

Group 3:
  SIFT, sel=0.01, query_template=Q1

Group 4:
  WIKI, sel=0.01, query_template=Q1
```

각 group에서 1000 queries를 sequential하게 실행한다.

```text
query_1 → prior update
query_2 → prior update
...
query_1000
```

---

## B.3 leakage 방지

중요하다.

EB-QAS는 이전 query 결과만 사용해야 한다.

금지:

```text
현재 query의 true cardinality를 prior에 먼저 반영
전체 query set의 평균 selectivity를 미리 계산해 prior로 사용
test query 결과를 train prior에 사용
```

허용:

```text
query t 실행 전:
  query 1 ... query t-1의 결과만 prior에 반영

query t 실행 중:
  current sample 결과만 likelihood로 사용

query t 실행 후:
  true cardinality를 query t+1 이후 prior에 반영
```

---

## B.4 cold-start / warm-start 분리

각 group의 1000 queries를 다음처럼 나눈다.

```text
queries 1~100:
  warm-up
  metric에는 포함하지 않거나 cold-start metric으로 따로 보고

queries 101~1000:
  evaluation
```

또는 전체를 online evaluation으로 보고, 시간 축을 나누어 표시한다.

```text
1~50
51~100
101~200
201~500
501~1000
```

이렇게 하면 history가 쌓이면서 EB-QAS의 sample 수와 Q-error가 어떻게 변하는지 볼 수 있다.

따라서 EB-QAS도 전체 latency에서 차이가 없을 수 있다. 하지만 다음 중 하나라도 보이면 의미가 있다.

```text
1. Q-error는 B1과 비슷한데 sample size가 줄었다.
2. sampling overhead가 줄었다.
3. plan_changed subset에서 latency가 개선되었다.
4. low-selectivity subset에서 latency가 개선되었다.
```

# 실험 E. ablation study

## E.1 목적

---

## E.2 variant

```text
B1:
  Exqutor Bernoulli Adaptive Sampling

EB-QAS-full:

EB-QAS-no-history:
  Beta(1,1) only
```

## E.3 해석

```text
EB-QAS-full > EB-QAS-no-history:
  history prior가 도움이 됨

EB-QAS-full > EB-QAS-no-stop:
  posterior early stopping이 sample 수를 줄임

EB-QAS-full > EB-QAS-no-reset:
  mismatch reset이 안정성에 필요함

large-kappa가 나쁘면:
  over-shrinkage 위험 확인

small-kappa가 B1과 비슷하면:
  prior가 너무 약하면 효과 제한
```

### 17.3 query-time estimation

```python
def ebqas_estimate(table, query, state, params):
    N = table.row_count
    n = 0
    s = 0

    while True:
        rows = uniform_sample(table, params.batch_size)

        hits = 0
        for row in rows:
            if distance(row.vector, query.vector) < query.threshold:
                hits += 1

        n += params.batch_size
        s += hits

        a_post = state.alpha + s
        b_post = state.beta + n - s

        p_hat = a_post / (a_post + b_post)
        c_hat = N * p_hat

        L, U = beta_credible_interval(
            a_post,
            b_post,
            confidence=0.95
        )

        # avoid division by zero
        L = max(L, 1.0 / (N * 10.0))

        q_post = max(p_hat / L, U / p_hat)

        if n >= params.n_min and q_post <= params.q_target:
            break

        if n >= state.n_cap:
            break

    return {
        "estimated_cardinality": c_hat,
        "sample_size": n,
        "hits": s,
        "posterior_alpha": a_post,
        "posterior_beta": b_post,
        "posterior_q_risk": q_post,
        "early_stopped": n < state.n_cap,
    }
```

### 17.4 after-execution update

```python
def update_after_execution(state, true_cardinality, table_size, posterior_info, params):
    """
    ★ Codex (b) fail 정정 적용본 (2026-05-23 23:10 KST · `EBQAS_구현_의사코드_20260523_231042.md` §4.2):
      1. mismatch 감지 → consecutive_mismatch streak 카운트
      2. streak >= mismatch_n_threshold 시 explicit mode switch
         (prior_mode="no_history" + Beta(1,1) reset + early_stop=False + update skip)
      3. stable_query_count >= n_recovery 시 history 회복 옵션
      4. mismatch query에서 w_mismatch 별도 weight
    """
    p_true = true_cardinality / table_size

    # 1. prior mismatch detection (99% credible interval)
    L_prior, U_prior = beta_credible_interval(
        state.alpha, state.beta, confidence=0.99
    )
    mismatch_this_query = (p_true < L_prior) or (p_true > U_prior)

    # 2. streak 카운터 갱신
    if mismatch_this_query:
        state.mismatch_count += 1
        state.consecutive_mismatch += 1
        state.stable_query_count = 0
    else:
        state.consecutive_mismatch = 0
        state.stable_query_count += 1

    # 3. ★ explicit mode switch — 반복 mismatch 시 B1 cap fallback
    if (
        state.consecutive_mismatch >= params.mismatch_n_threshold
        and state.prior_mode == "history"
    ):
        state.prior_mode = "no_history"
        state.alpha, state.beta = 1.0, 1.0
        state.kappa, state.mu = 2.0, 0.5
        state.early_stop = False        # B1 cap까지 무조건 sampling
        return                          # update skip — 잘못된 prior 방향 학습 차단

    # 4. ★ recovery — stable workload 시 history 회복 (선택)
    if (
        state.prior_mode == "no_history"
        and state.stable_query_count >= params.n_recovery
    ):
        state.prior_mode = "history"
        state.early_stop = True
        # alpha/beta/kappa는 Beta(1,1) base 그대로 — 누적 재시작

    # 5. ★ empirical-Bayes update — mismatch query는 w_mismatch 적용
    w_effective = (
        params.w_mismatch if mismatch_this_query else params.w
    )

    new_kappa = min(
        params.kappa_max,
        params.rho * state.kappa + w_effective
    )

    new_mu = (
        params.rho * state.kappa * state.mu
        + w_effective * p_true
    ) / (
        params.rho * state.kappa + w_effective
    )

    state.kappa = new_kappa
    state.mu = min(max(new_mu, 1e-9), 1.0 - 1e-9)
    state.alpha = state.mu * state.kappa
    state.beta = (1.0 - state.mu) * state.kappa

    # optional: update n_cap using Exqutor-style Q-error feedback
    # q_error = max(est / true, true / est)
    # state.n_cap = update_n_cap_with_momentum_lr(state.n_cap, q_error)
```

## 18. 구현 시 주의사항

### 18.1 double counting 금지

현재 query sample을 prior에도 넣고 likelihood에도 넣으면 안 된다.

올바른 순서:

```text
이전 query들:
  prior update

현재 query sample:
  likelihood

prior × likelihood:
  posterior

현재 query 실행 후:
  다음 query를 위한 prior update
```

잘못된 순서:

```text
현재 query sample으로 prior update
동일 sample로 likelihood 계산
→ 같은 증거를 두 번 사용
```

---

### 18.2 true cardinality 사용 시점

true cardinality는 query 실행 후에만 사용한다.

```text
planning time:
  prior + current sample만 사용

execution after:
  true cardinality로 state update
```

---

### 18.3 group key가 너무 세밀하면 안 됨

너무 세밀하면 모든 group이 cold-start가 된다.

나쁜 예:

```text
group key에 query vector hash를 그대로 넣음
→ 거의 매 query가 새로운 group
```

좋은 예:

```text
threshold bucket
query template
scalar predicate signature
```

---

### 18.4 group key가 너무 넓어도 안 됨

너무 넓으면 서로 다른 selectivity query가 섞인다.

나쁜 예:

```text
모든 DEEP query를 하나의 group으로 묶음
```

좋은 예:

```text
DEEP + threshold_bucket + query_template + predicate_signature
```

## 19. 성공 기준

EB-QAS가 adaptive sampling보다 낫다고 주장하려면 최소 하나 이상을 보여야 한다.

```text
1. B1과 같은 sample size에서 Q-error 감소
2. B1과 같은 Q-error에서 sample size 감소
3. low-selectivity에서 p95/p99 Q-error 감소
4. zero-hit 또는 extreme Q-error 감소
5. sampling overhead 감소
6. plan_changed subset에서 latency 감소
7. CaseB보다 낮은 overhead로 비슷한 Q-error 달성
```

가장 이상적인 결과:

```text
median Q-error ↓
p95 Q-error ↓
final sample size ↓
sampling overhead ↓
latency unchanged or ↓
```

전체 latency가 크게 줄지 않아도, sample size와 Q-error가 동시에 개선되면 의미가 있다. 다만 “latency 개선”을 강하게 주장하려면 plan-sensitive subset에서 별도 증거가 필요하다.

| ----------------------- | ----------------------------------- |
| cold-start              | EB-QAS ≈ B1                         |

| latency 전체 평균           | 차이가 작을 수 있음                         |
| plan-sensitive subset   | latency 개선 가능성 있음                   |

## 21. 최종 가설

본 실험의 핵심 가설은 다음이다.

> **H1.** 유사 query/predicate가 반복되는 workload에서 EB-QAS는 Exqutor B1보다 더 적은 current-query sample로 유사하거나 더 낮은 Q-error를 달성한다.

> **H2.** EB-QAS는 low-selectivity query에서 sample hit가 0개인 경우에도 prior shrinkage를 통해 zero-cardinality collapse를 줄이고, p95/p99 Q-error를 낮춘다.

> **H3.** EB-QAS의 posterior early stopping은 final sample size와 sampling overhead를 줄인다.

> **H4.** EB-QAS의 latency 개선은 전체 query 평균보다 plan_changed, low-selectivity, high-dimensional subset에서 더 잘 나타난다.

> **H5.** κ cap, decay, mismatch reset이 없으면 EB-QAS는 잘못된 query grouping에서 B1보다 악화될 수 있다.

## 22. 결론

EB-QAS는 distribution-aware stratification이 아니다. 데이터 분포를 미리 안다고 가정하지 않는다.

본 방법은 Exqutor의 adaptive sampling과 같은 uniform random sampling 기반을 유지하되, 과거 유사 query의 실행 피드백을 empirical-Bayesian prior로 누적한다. 현재 query에서는 sample 결과를 likelihood로 사용해 posterior를 계산하고, posterior Q-risk가 충분히 작으면 sampling을 조기 종료한다.

핵심 차이는 다음이다.

```text
Exqutor:
  이전 Q-error를 보고 sample size를 조절한다.

EB-QAS:
  이전 유사 query의 true selectivity를 prior로 저장하고,
  현재 sample과 결합해 posterior selectivity를 추정한다.
```

이 방식은 유사 query가 반복되는 workload에서 특히 의미가 있다. 반복된 history가 쌓이면 prior strength (\kappa)가 effective sample처럼 작동하고, 현재 query에서 필요한 sample 수를 줄일 수 있다. 다만 prior가 틀릴 경우 오히려 B1보다 나빠질 수 있으므로, κ cap, decay, mismatch reset, fallback이 반드시 필요하다.

실험에서는 Q-error뿐 아니라 final sample size, sampling overhead, latency, plan change를 함께 봐야 한다. 기존 Capstone 결과에서 CaseB는 Q-error 개선을 보였지만 latency 개선으로 강하게 연결되지 않았으므로, EB-QAS의 핵심 평가는 “Q-error 개선”뿐 아니라 **B1을 대체하면서 sample 수를 줄일 수 있는가**에 맞춰야 한다.
